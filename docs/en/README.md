# New-Human Orchestrator Usage Guide

Language policy note: this file is a deliberate public English guide. The repository's Korean output policy still applies to ordinary plans, reports, skill descriptions, agent metadata, PR text, and task handoff notes.

This guide is intentionally short.

Use `setup.sh` to create the reusable operating surface. Then use Q&A to choose and define the actual flow.

See the [System Dictionary](dictionary.md) for shared operating terminology.

The tracked canonical state in this repository is the Layer 0 System SSoT. Real Layer 1 User SSoT and Project SSoT, Layer 2 Project Work SSoT, and Layer 3 Silo Local / Test Evidence data are not canonical tracked data here.

Top-level functions:

1. layer operations
2. main/work branch operations
3. Layer 1 Project SSoT management
4. Project Contract Gate
5. Task/Issue/Silo operations
6. Runtime Set management
7. PR Review Loop
8. feedback/personality loop
9. setup/support surface management
10. User Layer / Personality System

Risky execution precondition checks are not a standalone feature. They are absorbed as lower gates under Task/Issue/Silo operation and Runtime Set management. Task-level `hypothesis_chain` records belong under Task/Issue/Silo operations, while User Layer / Personality System keeps user-specific User Personality and Feedback state outside the public repository.

Operating hypothesis management is a separate Layer 0 System SSoT metadata record. Operating hypotheses are not product feature hypotheses. They track why a task handling method, information gathering method, implementation plan, silo flow, PR loop, or review loop was selected and what bottlenecks it created.

The canonical location is `system/60-operating-hypotheses/`. Use that README for the current hypothesis list, `draft`/`active`/`closed`/`discarded` states, template, and promotion criteria. The task-local `hypothesis chain` that records execution failures and retries is a different record unit from the Layer 0 operating hypotheses that describe the operating method itself.

## Setup

Interactive setup:

```bash
./setup.sh
```

Default setup creates one project workspace from the project name:

```text
<workspace>/
├── AGENTS.md
├── user-layer/
├── <projectName>/01-project-ssot/
├── <projectName>/02-project-work-ssot/
├── sources/
├── silos/
└── shared-runtime/
```

Common non-interactive setup:

```bash
./setup.sh --quickstart --project-name sample --yes
./setup.sh --repo-skills --using-superpowers --yes
./setup.sh --init-config --yes
./setup.sh --init-user-layer --yes
./setup.sh --agent-browser --compound-engineering --yes
AGENT_BROWSER_SKIP_RUNTIME=1 ./setup.sh --agent-browser --yes
./setup.sh --none
```

The distributed repository protects its root `user-layer/` through `.gitignore` before setup. After every selected `setup.sh` action succeeds, setup removes the exact `/user-layer/` ignore rule; a failed setup leaves the rule in place.

`--all` installs or creates the full default environment, but excludes the project SSoT scaffold. Run `--create-project-ssot` separately because that scaffold needs an explicit project id and target path.

Create a project SSoT scaffold:

```bash
./setup.sh --create-project-ssot \
  --project-id <project-id> \
  --project-name "<project-name>" \
  --yes
```

Key options:

- `--all`: run every setup group.
- `--none`: exit without setup.
- `--repo-skills`: install this repository's repo skills.
- `--using-superpowers`: install `using-superpowers` from `obra/superpowers`.
- `--superpowers-workflow`: install the required Superpowers workflow skills.
- `--agent-browser`: install the `agent-browser` CLI/browser runtime and skill.
- `AGENT_BROWSER_SKIP_RUNTIME=1`: with `--agent-browser`, install only the skill file and skip the CLI/browser runtime.
- `--compound-engineering`: install Compound Engineering skills.
- `--init-config`: create local config files from examples.
- `--init-user-layer`: prepare `$CODEX_HOME/AGENTS.md`, the workspace router, and the User SSoT directory at the fixed `user-layer/` path. For an existing global `AGENTS.md`, setup offers backup-and-replace, delete-and-replace, or stop. For an existing `AGENTS.override.md`, it offers backup-and-delete, immediate deletion, or stop. These approvals remain required with `--yes`.
- `--create-project-ssot`: create a project SSoT scaffold.
- `--project-id <id>`, `--project-name <name>`, `--target <dir>`: set project SSoT scaffold values.
- `--force`: overwrite allowed local files generated by setup.
- `--yes`, `-y`: skip the final confirmation prompt.
- `--help`, `-h`: show help.

## What Setup Can Create

`setup.sh` can create most repeatable structure. However, `--all` does not create the project SSoT folders or their scaffold files:

- repo skills
- local config drafts
- a `user-layer/` User SSoT directory
- `$CODEX_HOME/AGENTS.md`, which routes Codex to the Layer 0 root AGENTS router and the User Layer source of truth
- project SSoT folders
- Project Work SSoT folders
- `sources/`, `silos`, and `shared-runtime` workspace folders
- dashboard files
- issue/task templates
- project contract template
- handoff templates and an initial PR body template
- coverage folders

The `templates/pr-description.md` generated by `setup.sh --create-project-ssot` is a scaffold starting point. Before submitting a PR, use `system/40-pr-review-loop/06-pr-template.md` as the formal source for required sections, criteria-by-criteria verification, Codex review, runtime handoff, and feedback/follow-up metadata.

`setup.sh` cannot honestly fill project-specific knowledge by itself. Product intent, real user flows, DB/API/auth boundaries, and architecture meaning still need repository analysis, LLM-assisted research, and user confirmation.

## Choose a Flow

Start with these questions:

1. Is there already a codebase?
2. Do you want to operate on one project or summarize many projects?
3. Is the immediate goal to create tasks, create a project knowledge base, or start a new product?
4. Is `project-contract-gate` available?
5. After the flow is defined, can the current setup actually run that flow?

## Example-to-Skill Links

- When adopting an existing project, use `projects-setup` to create or confirm the Project SSoT scaffold and project registration state, then use `project-contract-gate` to close unknown user goals and implementation boundaries.
- When researching existing GitHub repositories or local projects into a knowledge base, use `github-project-intake` to collect repository candidates, evidence, and apply/hold/exclude decisions. If a storage location is needed, use `projects-setup` to prepare the Project SSoT scaffold.
- When starting a new project, use `project-contract-gate` to close the first product definition and smallest slice, then use `projects-setup` to create the Project SSoT, contract, and task/silo templates.

## Readiness Check

After choosing a flow, check:

- the repo skills for the chosen example are installed: existing-project adoption starts with `projects-setup` and `project-contract-gate`; GitHub/project research starts with `github-project-intake` and, when storage is needed, `projects-setup`; new-project startup starts with `project-contract-gate` and `projects-setup`
- project SSoT location exists or can be scaffolded with `projects-setup`
- source repository or GitHub input is available
- `project-contract-gate` or an equivalent Q&A process can close unknowns
- task creation rules are available
- silo execution rules are available
- branch target matches the layer: the target Layer 0 main branch is `main-v3/main`, the target Layer 1 main branch is `project-{projectName}/main`, and target work branches use `main-v3/{taskname}` or `project-{projectName}/{taskname}`. Before migration, the current Layer 0 compatibility base is `main-v3/main` with `main-v3/{taskname}` work branches.
- `main-v3` and `project-{projectName}` are namespaces, not leaf branches
- the previous slash-based `project/<project-id>` model is treated as compatibility or migration context, not the target canonical model
