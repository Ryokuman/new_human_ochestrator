# 퍼스널리티 확정 인터뷰 가이드

## 목적

이 문서는 사용자 퍼스널리티와 취향 불변성을 "후보"에서 "확정 규칙"으로 올리기 위해 필요한 사용자 입력을 정리합니다.

사용자가 모든 항목을 한 번에 채울 필요는 없습니다. 모르는 항목은 `스킵`으로 두고, 이후 대화나 실제 PR 피드백으로 채워도 됩니다.

## 확정에 필요한 데이터

### 1. 절대 규칙

아래 항목은 사용자 답변으로 확정된 규칙과 아직 확인이 필요한 규칙을 나눕니다.

```markdown
## 절대 규칙

- [x] 모든 사람이 읽는 프롬프트와 보고서는 한국어로 작성한다.
- [x] 사일로는 작업마다 필요한 레포지토리만 새로 clone해서 격리된 작업 공간을 만든다.
- [x] 사일로는 문제 해결에 필요하면 격리 작업 공간 안에서 코드를 매우 자유롭게 수정할 수 있다.
- [x] 사일로는 절대로 `main`, `dev`, `develop`, `master` 같은 보호 브랜치에 직접 수정, commit, push하지 않는다.
- [x] 사일로는 항상 작업 브랜치를 새로 만들어 작업한다.
- [x] 사일로는 PR description에 `SSoT 승격 후보`와 `승격하지 않을 항목`을 반드시 작성한다.
- [ ] 실제 기능 검증이 필요한 작업은 agent-browser 시연 또는 동등한 런타임 증거를 우선한다.
- [ ] 완료/미완료/목표 밖 산출물/다음 행동을 분리해서 보고한다.
- [ ] 사용자 목표가 분석/설계일 때는 코드 수정으로 바로 넘어가지 않는다.

추가 절대 규칙:
- 
```

### 4. 승인 경계

어디까지 자율로 해도 되고, 어디서 멈춰야 하는지 적습니다.

```markdown
## 승인 경계

자율 진행 가능:
- 문서 초안 생성
- result 내부 구조 정리
- QA/버그 후보 정리
- 

명시 승인 필요:
- PR 생성
- branch push
- Notion SoT 갱신
- 

사일로에 명시적으로 허용:
- 필요한 레포지토리만 새로 clone
- 보호 브랜치가 아닌 새 작업 브랜치 생성
- 격리 clone 내부 source code 수정
- 격리 clone 내부 generated output 수정
- 문제 해결에 필요한 과감한 수정과 실험

조건:
- 작업 결과는 반드시 새 브랜치와 PR로만 제출한다.
- main/dev/develop/master에는 직접 손대지 않는다.
- 코드가 망가지면 clone/branch를 폐기하면 되므로, 사일로 내부 실험 자체를 과도하게 막지 않는다.

절대 자동 금지:
- production 데이터 변경
- secret 값 읽기/기록
- force push
- main/dev/develop/master 직접 commit 또는 push
- 
```

### 5. 사일로 운영 취향

동적 사일로가 어떻게 일해야 하는지 적습니다.

```markdown
## 사일로 운영 취향

사일로가 자율로 해도 되는 것:
- 필요한 레포지토리만 clone
- 새 작업 브랜치 생성
- 격리 작업 공간 안에서 자유로운 코드 수정
- 문제 해결을 위한 실험적 수정
- 테스트, 빌드, QA, agent-browser 검증

사일로가 메인 오케스트레이터에게 물어야 하는 것:
- 보호 브랜치에 직접 영향을 줄 수 있는 행동
- production 데이터 또는 secret 관련 행동
- SSoT 전역 규칙을 바꿔야 하는 판단
- 원래 task/issue보다 큰 scope로 번지는 판단

사일로가 PR description에 반드시 남겨야 하는 것:
- 작업 요약
- 검증 결과
- SSoT 승격 후보
- 승격하지 않을 항목과 이유
- 보호 브랜치에 직접 손대지 않았다는 브랜치/작업공간 정보

사일로 내부 발견을 SSoT로 승격해야 하는 기준:

승격하지 않아도 되는 기준:
```

### 10. 퍼스널리티 갱신 방식

사용자 피드백을 어떻게 규칙으로 승격할지 정합니다.

```markdown
## 퍼스널리티 갱신 방식

전역 규칙으로 바로 승격해도 되는 경우:
- 사용자가 "이건 영구 규칙으로 하자"라고 말함
- 

후보로만 둘 경우:
- 한 번 나온 피드백
- 특정 사일로/PR에만 해당하는 피드백
- 

승격 전에 다시 물어야 하는 경우:
- 기존 규칙과 충돌
- 적용 범위가 넓음
- 코드 수정 방식에 큰 영향
-
```

## 가장 먼저 물어볼 질문

한 번에 다 채우기 어렵다면 아래 3개만 먼저 답하면 됩니다.

1. 모든 사람이 읽는 프롬프트와 보고서는 한국어 우선, 이건 전역 확정 규칙으로 박아도 되나요?
2. source code 수정, generated output 수정, PR 생성은 항상 명시 승인 후 진행해야 하나요?
3. 사일로가 PR description에 `SSoT 승격 후보`와 `승격하지 않을 항목`을 반드시 쓰는 것을 확정 규칙으로 둘까요?

답변 반영:

1. 예. 한국어 우선은 전역 확정 규칙입니다.
2. 아니오. 사일로는 필요한 레포지토리만 clone하고 새 브랜치에서 자유롭게 수정합니다. 단, main/dev/develop/master 같은 보호 브랜치에는 절대 직접 손대지 않습니다.
3. 예. PR description의 `SSoT 승격 후보`와 `승격하지 않을 항목`은 확정 규칙입니다.
