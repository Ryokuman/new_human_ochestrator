## 운영 가설

PR의 각 검증을 `테스트 목적`, `준비 조건과 입력`, `실행 방법`, `기대 결과`, `실제 결과`, `검증 한계`, `재실행 명령`으로 설명하면, 사용자는 많은 파일·커밋·테스트 코드를 직접 읽지 않고도 테스트가 변경 위험을 충분히 다루는지 판단할 수 있습니다.

## 채택 이유

명령과 pass 수치는 재현에는 유용하지만 테스트가 어떤 상황을 만들고 무엇을 성공으로 보는지 설명하지 않습니다. 보장 내용만 요약해도 입력, 실행 과정과 검증 한계가 빠지면 사용자는 결국 테스트 코드를 읽어야 합니다.

## 취합한 정보

- 사용자는 PR 검토에서 모든 파일과 커밋을 읽는 방식은 지속 가능하지 않다고 밝혔습니다.
- 첫 적용 PR은 기능 직접 검증, 함께 동기화된 공통 회귀 검증, 형식 검사를 섞어 나열했습니다.
- 같은 명령도 목적, 입력, 기대 결과, 한계를 설명하면 코드 없이 검토할 수 있었습니다.

## 기존 방식의 문제

- 실행 명령과 pass 수치가 사용자 판단 자료처럼 제시됩니다.
- 테스트가 원하는 동작과 실제로 만드는 입력을 알 수 없습니다.
- 자동 검증이 다루지 못하는 범위가 테스트별로 드러나지 않습니다.
- 직접 기능 검증과 공통 회귀·형식 검사의 중요도가 구분되지 않습니다.

## 예상 병목

- 테스트 수가 많은 PR은 본문이 길어질 수 있습니다.
- 구현자가 실제 테스트 코드보다 넓은 보장을 과장해 적을 수 있습니다.
- 반복되는 준비 조건을 매 테스트마다 복사하면 유지 비용이 커질 수 있습니다.

## 적용한 작업 방식

- 핵심 결론은 본문 위쪽에 두고 개별 테스트 계약은 접기 영역을 사용할 수 있게 합니다.
- 각 계약은 목적, 준비/입력, 방법, 기대·실제 결과, 한계, 명령을 모두 가집니다.
- 직접 기능 검증, 공통 회귀 검증, 형식 검사를 분리합니다.
- 재실행 명령은 기본 판단 자료가 아니라 재현용 세부 정보로 둡니다.

## 적용 범위

- 0계층 PR 본문 작성 기준과 중앙 템플릿
- test-writer 역할 규칙과 prompt
- project scaffold가 생성하는 PR 본문 템플릿
- 사용자별 설명 선호는 커밋하지 않는 User Layer 규칙으로 보조합니다.

## 사람 확인 지점

- 테스트 코드를 읽지 않고도 목적, 방법, 기대 결과와 한계를 이해할 수 있는지 확인합니다.
- 접기 영역을 열지 않아도 머지 판단에 필요한 핵심 결론이 충분한지 확인합니다.
- 테스트가 많은 PR에서 모든 계약을 상세 작성할지 위험 기반으로 줄일지 재검증합니다.

## 유지할 것

- 코드 없이 이해 가능한 테스트 목적과 방법
- 기대 결과와 실제 결과의 분리
- 테스트별 검증 한계
- 직접 검증, 공통 회귀, 형식 검사의 분류

## 버릴 것
