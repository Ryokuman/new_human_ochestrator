# PR 리뷰와 승격 판단

## 목적

PR은 단순히 코드를 머지하는 절차가 아닙니다.

PR은 사일로가 발견한 로컬 issue/task 중 무엇을 SSoT의 메인 이슈/태스크로 승격할지 판단하는 시점입니다.

## PR 본문 필수 섹션

사일로가 PR을 만들 때 본문에는 아래 섹션이 있어야 합니다.

```markdown
## 무엇을 했는가

## 연결된 SSoT 항목

## 작업 공간과 브랜치

## 변경 상세

## 그래서 무엇이 되었는가

## 검증

## 사일로에서 새로 발견한 항목

## SSoT 승격 후보

## 승격하지 않을 항목

## 메인 오케스트레이터 판단 필요

## 사용자 피드백 반영 여부
```

## PR 본문 설명 기준

PR 본문은 결과만 나열하지 않고, 처음 보는 리뷰어가 변경 이유와 안전성을 판단할 수 있게 써야 합니다.

특히 converter, renderer, runner, generated output, data mapping, coverage 보정처럼 원인 추적이 중요한 작업은 아래 순서를 기본 구조로 삼습니다.

```text
문제 정의:
- 어떤 coverage/task/issue를 줄이거나 종결하려는가
- 초기 수치, 현재 수치, 목표 수치는 무엇인가

기존 동작:
- 기존 코드는 어떤 입력을 어떻게 처리했는가
- 어떤 필터, 매핑, 렌더링, runner 판정이 적용됐는가

문제가 된 이유:
- 그 기존 동작이 어떤 실제 입력이나 evidence에서 실패했는가
- 단순 증상 대신 누락/과다/오분류/불안정 파싱 같은 방향을 명시한다

변경 상세:
- 파일별로 무엇을 바꿨는가
- 변경한 함수나 정책이 어떤 역할을 하는가
- 왜 이 접근이 scope 안의 해결인지 설명한다

결과:
- 기준 run/report와 변경 후 run/report를 적는다
- coverage 개선형 task는 `초기 n -> 변경 후 n -> 목표 0` 또는 이에 준하는 현재/목표 수치를 적는다
- code 수정 완료, runner 보정 완료, source/data 확인 필요, 정책 후속 필요를 분리한다

검증:
- 실행한 테스트, generation, runner, agent-browser 여부를 적는다
- 실행하지 않은 검증이 있으면 이유를 적는다

남은 위험:
- 아직 해결하지 않은 항목과 이유를 page/item 단위로 적는다
- SSoT 승격 후보와 승격하지 않을 항목을 분리한다
```

좋지 않은 PR 본문:

- “기본 버튼을 복원했다”처럼 변경 결과만 쓰고, 어떤 입력이 왜 버려졌는지 설명하지 않는다.
- “시스템 버튼으로 버리지 않았다”처럼 내부자 표현만 쓰고, 그 행위가 파싱/변환/렌더링/runner 중 어디에서 일어나는지 설명하지 않는다.
- coverage 수치가 줄었다고만 쓰고, 기준 run과 변경 후 run, 남은 목표를 적지 않는다.

좋은 PR 본문:

- “suffix 없는 버튼”처럼 헷갈릴 수 있는 용어를 실제 예시와 함께 정의한다.
- 기존 코드가 해당 데이터를 제외한 조건과 그 조건이 문제를 만든 이유를 분리한다.
- 변경 파일, 함수 역할, 변경 메커니즘, 결과 수치, 남은 위험을 한 흐름으로 연결한다.

## 승격 후보 기준

사일로 내부 이슈/태스크를 SSoT로 승격하는 기준:

| 기준 | 설명 |
|---|---|
| 반복 가능성 | 다른 기능/레포에서도 반복될 가능성이 있음 |
| 독립 실행성 | 별도 task로 쪼개 수행 가능 |
| 영향 범위 | 현재 PR scope 밖에 영향이 있음 |
| 사용자 취향 관련성 | 에이전트 행동 규칙이나 취향 불변성 갱신과 관련 있음 |
| 검증 필요성 | 별도 QA/테스트가 필요함 |
| 승인 필요성 | 사용자 또는 메인 승인이 필요한 변경임 |

## 브랜치 안전 기준

사일로 PR은 아래 조건을 만족해야 리뷰 대상으로 봅니다.

- 필요한 레포지토리만 새로 clone한 격리 작업 공간에서 작업했음
- `main`, `dev`, `develop`, `master` 같은 보호 브랜치에서 직접 작업하지 않았음
- 새 작업 브랜치에서 수정했음
- 보호 브랜치에 직접 commit 또는 push하지 않았음
- 결과를 PR로 제출했음

이 조건을 만족하지 않으면 메인 오케스트레이터는 머지 리뷰보다 브랜치 안전 문제를 먼저 처리합니다.

## 승격하지 않을 기준

SSoT로 승격하지 않는 경우:

- 현재 PR에서 이미 해결됨
- 일회성 local cleanup
- 재현 불가
- 기존 issue/task와 중복
- scope 밖이지만 근거가 약함
- 사용자 취향 규칙과 무관한 사소한 구현 메모

## 머지 시 보고

PR 생성과 PR 머지는 별도 승인 단위입니다.

에이전트는 사용자가 `approve`, `LGTM`, `머지하세요`, `머지해도 됩니다`, `1. 머지`처럼 머지를 명시한 경우에만 PR을 머지합니다.

`진행해`, `작업 이어가`, `PR 만들어`, `main 업데이트`, `1. 승인`은 작업 진행 또는 PR 생성 승인일 수 있지만, 머지 승인으로 해석하지 않습니다.

PR이 머지될 때 메인 오케스트레이터는 아래를 보고합니다.

```text
머지 결과:
- 머지된 PR:
- state:
- mergedAt:
- mergeCommit:
- 해결된 SSoT issue/task:
- 새로 승격된 issue/task:
- 승격하지 않은 로컬 발견:
- 이유:
- 사용자 피드백 반영:
- 다음 사일로 후보:
```

## 리뷰 라운드

PR 리뷰 루프는 여러 번 돌 수 있습니다.

```text
사일로 PR 생성
-> 메인 리뷰
-> 재작업 요청
-> 사일로 수정
-> PR 업데이트
-> 메인 재리뷰
-> 머지 또는 추가 재작업
```

각 라운드는 PR 기록에 남깁니다.

## 메인 리뷰 체크리스트

- 원래 issue/task 해결 여부
- 변경 범위가 허용 scope 안인지
- 보호 브랜치에 직접 손대지 않았는지
- 새 작업 브랜치에서 작업했는지
- 검증 결과가 acceptance criteria를 덮는지
- 사용자 취향 규칙을 위반하지 않았는지
- 사일로 발견 항목 중 승격해야 할 것이 빠지지 않았는지
- 승격하지 않을 항목의 이유가 충분한지
- 다음 사일로로 넘길 작업이 있는지
