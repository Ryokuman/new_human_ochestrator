# 계층 구조와 관리 원칙

## 목적

이 문서는 메인 오케스트레이터가 어떤 계층의 데이터를 어디에 저장하고, 무엇을 승격하거나 격리해야 하는지 정합니다.

## 계층

```text
0계층: Root / Global
1계층: Project SSoT
2계층: Project Work SSoT
3계층: Silo Local
```

## 0계층: Root / Global

0계층은 작업 내용을 직접 관리하지 않습니다.

0계층이 관리하는 것:

- 계층 구조
- 계층별 책임
- 사일로 생성 방법
- Project SSoT와 Project Work SSoT 기본 구조 생성 방법
- 공통 YOLO 정책
- 보호 브랜치 정책
- secret/config 주입 방식
- shared runtime registry/status 템플릿과 생성/삭제 규칙
- 사용자 퍼스널리티와 전역 취향 규칙
- 공통 skill
- 프로젝트 등록, 연결, 분리, 승격 규칙

0계층이 하지 않는 것:

- 프로젝트 issue/task 직접 관리
- 프로젝트 QA backlog 직접 관리
- 사일로 local finding 직접 저장
- 프로젝트 내부 SSoT 덮어쓰기

## 1계층: Projects

1계층은 실제 프로젝트가 시작된 뒤 생기는 Project SSoT입니다. 프로젝트의 존재, 연결 방식, 기준 계약, 장기 의사결정, 하위 작업 SSoT 위치를 관리합니다.

프로젝트는 기본적으로 이 저장소에 직접 커밋하지 않습니다.

현재 `my_ochestrator`의 `main-v3/main`에는 실제 프로젝트 실데이터가 없습니다. `system/`은 Project SSoT를 만드는 규칙과 템플릿만 보관하며, 실제 1계층 Project SSoT는 프로젝트가 등록된 뒤 해당 project 기준 브랜치나 외부 SSoT 위치에 생성됩니다.

권장 연결 방식:

- fork
- 목표 `project-{projectName}/main` 장기 계층 메인 브랜치
- 현재 호환 `project-{projectName}` 장기 브랜치
- git submodule
- external clone
- project registry
- secret/config reference

`project-{projectName}/main` 브랜치는 별도 fork를 만들지 않을 때 사용하는 프로젝트별 Project SSoT 장기 계층 메인 브랜치입니다. 이 브랜치는 `main-v3/main`에 머지할 기능 브랜치가 아니라, 특정 프로젝트의 repo 연결 상태, 코드 분석 요약, Project SSoT 색인, project contract, decision/ADR, 운영 기준을 보관하는 장기 브랜치입니다. `project-{projectName}` 자체는 namespace이며 브랜치로 만들지 않습니다. 현재 마이그레이션 전 호환 상태에서는 `project-{projectName}` 브랜치를 기준 브랜치로 해석할 수 있습니다.

기존 slash 기반 `project/<project-id>` 브랜치 모델은 전환/호환 필요 항목으로만 다룹니다. 이미 존재하는 브랜치나 문서 링크는 바로 폐기하지 않고, 해당 프로젝트의 기준 브랜치를 `project-{projectName}/main` 형식으로 전환할지 또는 호환 유지할지 확인한 뒤 갱신합니다.

project 계층 메인 브랜치의 변경은 기본적으로 root 0계층으로 합치지 않습니다. project 브랜치에서 반복 가능한 공통 운영 규칙이 발견되면, 그 규칙만 별도 0계층 업데이트 후보로 분리합니다.

1계층의 `projects/`는 Project SSoT/registry 성격의 자료를 관리합니다. 실제 제품 소스코드는 `projects/` 아래에 두지 않고, 별도 repo/worktree, fork, submodule, external clone, 또는 gitignore된 로컬 source 위치에 둡니다.

1계층의 project overview, registry, config, contract, decision/ADR은 특정 task/silo의 구현 준비 상태를 담지 않습니다. 특정 `TASK-NNNN` 전용 문장, `Initial Mock Data`/`Test Inputs` 상세, 단일 API/page 실행 계약, endpoint 추가 필요성, 사일로 진행 상태는 2계층 Project Work SSoT의 task/runbook 또는 3계층 사일로로 내려보냅니다. 1계층에는 프로젝트 정본 위치, repo/source/harness/DB/API/auth 참조, project contract, decision/ADR, 하위 2계층 위치 인덱스, 반복 가능한 project-level 운영 기준만 남깁니다.

task 계약이 BE/FE 독립 git submodule을 요구하면 상위 제품 repo는 BE와 FE의 두 gitlink를 둔 submodule host로만 다룹니다. 상위 제품 repo에는 `.gitmodules`, gitlink, 빌드/보안 제외 설정처럼 연결과 격리에 필요한 최소 변경만 남기고, 제품 BE/FE 구현 변경은 각 독립 submodule repo에서 관리합니다. BE/FE/page/harness-scenario를 단일 기능 repo로 묶는 것은 task 계약이 그렇게 명시한 경우에만 허용합니다. task별 기능 repo/submodule 소유권은 project registry/config 또는 Project SSoT에서 참조 위치로 기록하고, 실제 제품 코드 원문은 0계층이나 1계층 overview에 복사하지 않습니다.

`vite-harness` 계열 repo는 스토리북 같은 재사용 하네스 라이브러리입니다. 제품별 시나리오, seed, demo, adapter는 하네스 라이브러리 원본 repo가 아니라 task 계약이 지정한 기능 submodule repo 또는 Project Work SSoT에 둡니다. 1계층에는 어떤 하네스를 참조하는지와 제품별 adapter/시나리오 정본 위치만 남깁니다.

프로젝트 등록/setup 시 DB를 사용하는 프로젝트는 DB schema 정본 위치 또는 schema 요약 위치를 project registry/config 또는 Project SSoT에 기록해야 합니다. Docker, compose, migration, startup script처럼 DB schema가 자동 생성되거나 갱신되는 경로가 있으면 setup 문서에 schema 적용 경로도 함께 기록합니다. 0계층은 실제 테이블/컬럼을 기록하지 않고, setup 시 어떤 종류의 정본 위치와 적용 경로를 남겨야 하는지만 정의합니다.

목표 모델에서 `project-{projectName}/main` 브랜치가 존재하는 프로젝트의 1계층 Project SSoT 변경은 해당 브랜치에서 판 `project-{projectName}/<branch-name>` 작업 브랜치에서 수행합니다. 현재 호환 상태에서는 `project-{projectName}`와 `project-{projectName}-<branch-name>`을 사용합니다. project 계층 메인 브랜치에는 직접 커밋하지 않습니다. 2계층 task, issue, QA, runbook, coverage 원문은 Project Work SSoT 기준 위치에서 관리하고, `docs/*`, `chore/*`, `silo/*`, 또는 0계층 공통 규칙 브랜치에서 직접 수정하지 않습니다. 공통 템플릿, scaffold 로직, repo skill, agent prompt처럼 0계층 규칙 자체를 바꾸는 경우에는 목표 `main-v3/{taskname}` 또는 현재 호환 `main-v3/{taskname}` 작업 브랜치를 사용합니다.

1계층이 관리하는 것:

- 프로젝트 id
- Project SSoT 위치
- 프로젝트 repo/fork/submodule 연결 정보
- project contract
- project decision/ADR
- runtime / DB / API / auth 참조
- 공용 서비스 여부
- 사일로 대상 repo 여부
- 보호 브랜치
- secret/config source
- shared runtime registry/status 위치
- DB 사용 여부, schema 정본 위치 또는 schema 요약 위치
- Docker/compose/migration/startup script의 schema 적용 경로
- 반복 적용되는 schema 정본 위치와 seed/test input 분리 원칙의 하위 2계층 Project Work SSoT 참조

1계층에 두지 않는 것:

- task/issue/QA 원문
- silo local 로그
- 단일 task mock data/test input
- 단일 PR 임시 판단

## 2계층: Project Work SSoT

2계층은 프로젝트 내부의 실제 작업 운영 상태입니다. task/issue/QA/runbook/coverage처럼 실행 중 계속 변하는 work item과 검증 기록을 관리합니다.

2계층이 관리하는 것:

- issue
- task
- QA 결과
- handoff
- project-specific skill
- coverage/scoring 기준
- project-specific runbook
- 외부 서비스, 인증 provider, fixture, runtime, L gate 같은 프로젝트별 실행 처방
- 프로젝트 상태 대시보드

2계층 데이터는 해당 Project Work SSoT에 저장합니다. 0계층 `system/`이나 1계층 Project SSoT 기준 정보 영역에 저장하지 않습니다.

Project Work SSoT는 최소한 아래 네 가지 운영 구성을 가져야 합니다.

- 태스크 생성/관리
- L 기준 생성/관리
- 이슈 관리
- 대시보드

이 네 가지는 모두 2계층 Project Work SSoT에 속합니다. 0계층 `system/`은 이 구조가 필요하다는 공통 규칙과 템플릿만 관리합니다.

0계층으로 복사하지 않는 프로젝트 내부 자료:

- 특정 프로젝트의 실제 태스크 본문
- 특정 프로젝트의 실제 이슈 본문
- L runner 결과
- page 목록
- coverage report 내용
- 프로젝트별 대시보드/보고서 실행 결과

Project Work SSoT에 dashboard, task format, issue format, L 기준이 필요하면 0계층에는 실제 프로젝트 산출물을 올리지 않습니다. 0계층은 `setup.sh` 셋업 흐름이나 skill만 제공하고, 생성 결과는 2계층 Project Work SSoT에 둡니다.

프로젝트별 evidence는 coverage 판단 근거이므로 Project Work SSoT 내부에 보존할 수 있습니다. 단, evidence 원본이 제품 소스코드나 대용량 실행 산출물인 경우에는 Project Work SSoT에 위치와 요약을 남기고 원본은 프로젝트 정책에 맞는 외부/로컬 저장 위치에 둡니다.

외부 서비스, 인증 provider, 화면별 QA, DB fixture, runtime harness, L 단계 같은 좁은 실행 처방은 2계층 Project Work SSoT 또는 task 계약에서 관리합니다. 0계층 `system/`은 이 항목을 어떤 판단 근거로 Project Work SSoT에 내려야 하는지와, 통제된 검증과 실제 사용자 경로를 섞지 않는 원칙만 관리합니다.

2계층 Project Work SSoT를 쓰기 전에는 기준 Work SSoT 위치와 함께 목표 기준 `project-{projectName}/main` 브랜치, 목표 작업 `project-{projectName}/<branch-name>` 브랜치를 확인합니다. 현재 호환 상태에서는 `project-{projectName}`와 `project-{projectName}-<branch-name>`을 확인합니다. 기존 slash 기반 `project/<project-id>` 브랜치가 있으면 전환/호환 상태를 먼저 확인하고, 그 브랜치에서 판 작업 브랜치가 현재 기준인지 검증합니다. 다른 브랜치에 Project Work SSoT diff가 있으면 바로 이어 쓰지 않고 `기준 아님`, `이관 후보`, `위험`, `사용자 판단 필요`로 분리합니다.

오래된 작업 브랜치의 project SSoT diff를 평가할 때는 비교 기준을 나눕니다. 공통 규칙 drift는 0계층 계층 메인 브랜치 기준으로 보고, Project SSoT 또는 Project Work SSoT의 추가/삭제/이관 여부는 해당 project 계층 메인 브랜치 기준으로 봅니다. 현재 호환 기준은 `main-v3/main`와 `project-{projectName}`이고, 목표 기준은 `main-v3/main`과 `project-{projectName}/main`입니다. 기존 slash 기반 `project/<project-id>` 기준 diff는 전환/호환 증거로 분리합니다. 최종 트리 차이인 `base..branch`와 브랜치 고유 변경인 `base...branch`를 구분해 보고하고, 둘을 섞어 이관 완료나 삭제 완료로 판단하지 않습니다.

Project SSoT 또는 Project Work SSoT 삭제는 이관 또는 폐기 근거가 있는 파일에만 허용합니다. 삭제 대상은 먼저 `이관 확인됨`, `미이관`, `중복`, `폐기 후보`, `사용자 판단 필요`로 분류합니다. `todo`, `in_progress`, active issue, QA evidence, handoff, source doc이 포함된 경우에는 삭제 PR을 만들기 전에 대상 `project-{projectName}/main` 브랜치, 현재 호환 `project-{projectName}` 브랜치, 호환 중인 slash 기반 `project/<project-id>` 브랜치, 또는 SSoT 경로에서 동등한 정보가 살아 있는지 확인합니다.

프로젝트별 shared runtime registry/status도 1계층 Project SSoT의 registry/config 또는 2계층 Project Work SSoT에 둡니다. 0계층은 `shared-runtime/<project-id>/<runtime-name>/` 같은 일반 경로 후보, 필드 템플릿, `add-shared-runtime`, `delete-shared-runtime` 규칙만 관리합니다.

## 3계층: Silo Local

3계층은 사일로가 작업 중 임시로 갖는 local 상태입니다.

3계층이 관리하는 것:

- local finding
- local issue/task
- 실험 로그
- 임시 검증 결과
- task가 참조한 shared runtime branch, commit, port, health check 결과
- PR description 초안
- evidence/follow-up 후보
- 처리하지 않고 남긴 항목

3계층 데이터는 PR 전까지 Project SSoT나 Project Work SSoT에 바로 쓰지 않습니다.

PR 시점에 메인 오케스트레이터가 승격 여부를 판단합니다.

3계층 사일로는 제품 소스코드 저장 위치가 아니라 task 실행 상태를 담는 임시 작업 단위입니다. 사일로 안에 repo clone이 있을 수는 있지만, 그 clone은 해당 task 수행을 위한 폐기 가능한 source workspace이며 사일로 개념 자체와 동일하지 않습니다.

## 승격 규칙

```text
Silo Local
-> PR description
-> Main Orchestrator Review
-> Project Work SSoT Issue/Task
-> 필요 시 0계층 전역 규칙 후보
```

승격할 수 있는 것:

- 반복 가능한 버그
- 프로젝트 전체에 영향을 주는 문제
- 별도 task로 수행 가능한 일
- 프로젝트 전용 skill이 필요한 패턴
- 전역 사용자 취향이나 사일로 운영 규칙에 영향을 주는 피드백

승격하지 않는 것:

- 현재 PR에서 해결된 일회성 문제
- 근거가 약한 추측
- 특정 사일로의 임시 실험 로그
- 재현되지 않은 문제
- 프로젝트 내부에만 의미 있는 정보를 0계층으로 올리는 것

## 프로젝트 자료 커밋 정책

프로젝트 내부 자료는 기본적으로 이 저장소에 커밋하지 않습니다.

기본 원칙:

- 0계층 저장소는 공통 운영 규칙만 커밋합니다.
- 프로젝트 자료는 project repo, fork, 목표 `project-{projectName}/main` 브랜치, 현재 호환 `project-{projectName}` 브랜치, 호환 중인 기존 slash 기반 `project/<project-id>` 브랜치, submodule, external clone, SSoT에 둡니다.
- `project-{projectName}/main` 브랜치는 프로젝트별 정보 보관용 장기 계층 메인 브랜치이며 0계층 병합 대상이 아닙니다.
- 이 저장소 0계층에 프로젝트 자료를 합치려면 왜 코어 저장소에 필요한지 별도 0계층 업데이트 후보로 검토합니다.
- Project SSoT와 Project Work SSoT의 기본 구조가 반복적으로 필요하다는 요구는 프로젝트 자료 자체가 아니라 0계층 셋업 규칙입니다. 이 경우 root 저장소 `main-v3/main`에는 `setup.sh` 흐름, 템플릿, repo skill만 추가합니다.

## 메인 오케스트레이터 판단 순서

