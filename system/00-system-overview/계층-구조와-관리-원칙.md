# 계층 구조와 관리 원칙

## 목적

이 문서는 메인 오케스트레이터가 어떤 계층의 데이터를 어디에 저장하고, 무엇을 승격하거나 격리해야 하는지 정합니다.

## 계층

```text
0계층: Root / Global
1계층: Projects
2계층: Project Internal
3계층: Silo Local
```

## 0계층: Root / Global

0계층은 작업 내용을 직접 관리하지 않습니다.

0계층이 관리하는 것:

- 계층 구조
- 계층별 책임
- 사일로 생성 방법
- project SSoT 기본 구조 생성 방법
- 공통 YOLO 정책
- 보호 브랜치 정책
- secret/config 주입 방식
- shared runtime registry/status 템플릿과 생성/삭제 규칙
- 사용자 퍼스널리티와 전역 취향 규칙
- 공통 skill
- 프로젝트 등록, 연결, 분리, 승격 규칙

0계층이 하지 않는 것:

- 프로젝트 issue/task 직접 관리
- 프로젝트 QA backlog 직접 관리
- 사일로 local finding 직접 저장
- 프로젝트 내부 SSoT 덮어쓰기

## 1계층: Projects

1계층은 프로젝트의 존재와 연결 방식을 관리합니다.

프로젝트는 기본적으로 이 저장소에 직접 커밋하지 않습니다.

권장 연결 방식:

- fork
- `project/<project-id>` 장기 브랜치
- git submodule
- external clone
- project registry
- secret/config reference

`project/*` 브랜치는 별도 fork를 만들지 않을 때 사용하는 프로젝트별 정보 보관 브랜치입니다. 이 브랜치는 `main-v2`에 머지할 기능 브랜치가 아니라, 특정 프로젝트의 repo 연결 상태, 코드 분석 요약, SSoT 색인, 운영 메모를 보관하는 장기 브랜치입니다.

`project/*` 브랜치의 변경은 기본적으로 root `main-v2`로 합치지 않습니다. `project/*`에서 반복 가능한 공통 운영 규칙이 발견되면, 그 규칙만 별도 `main-v2` 업데이트 후보로 분리합니다.

1계층의 `projects/`는 프로젝트 SSoT/registry 성격의 자료를 관리합니다. 실제 제품 소스코드는 `projects/` 아래에 두지 않고, 별도 repo/worktree, fork, submodule, external clone, 또는 gitignore된 로컬 source 위치에 둡니다.

`project/<project-id>` 브랜치가 존재하는 프로젝트의 2계층 project SSoT 작업은 해당 `project/<project-id>`에서 판 별도 worktree의 파생 브랜치에서 수행합니다. `project/<project-id>` 장기 브랜치에는 직접 커밋하지 않습니다. task, issue, QA, decision, dashboard, source doc 원문을 `docs/*`, `chore/*`, `silo/*`, 또는 `main-v2` 파생 공통 규칙 브랜치에서 직접 수정하지 않습니다. 공통 템플릿, scaffold 로직, repo skill, agent prompt처럼 0계층 규칙 자체를 바꾸는 경우에만 `main-v2` 파생 단기 브랜치를 사용합니다.

1계층이 관리하는 것:

- 프로젝트 id
- 프로젝트 SSoT 위치
- 프로젝트 repo/fork/submodule 연결 정보
- 공용 서비스 여부
- 사일로 대상 repo 여부
- 보호 브랜치
- secret/config source
- shared runtime registry/status 위치

## 2계층: Project Internal

2계층은 프로젝트 내부의 실제 운영 상태입니다.

2계층이 관리하는 것:

- issue
- task
- QA 결과
- handoff
- project decision/ADR
- project-specific skill
- coverage/scoring 기준
- project-specific runbook
- 외부 서비스, 인증 provider, fixture, runtime, L gate 같은 프로젝트별 실행 처방
- 프로젝트 상태 대시보드

2계층 데이터는 해당 프로젝트 SSoT에 저장합니다. 0계층 `system/`에 저장하지 않습니다.

프로젝트 SSoT는 최소한 아래 네 가지 운영 구성을 가져야 합니다.

- 태스크 생성/관리
- L 기준 생성/관리
- 이슈 관리
- 대시보드

이 네 가지는 모두 2계층 Project Internal에 속합니다. 0계층 `system/`은 이 구조가 필요하다는 공통 규칙과 템플릿만 관리합니다.

0계층으로 복사하지 않는 프로젝트 내부 자료:

- 특정 프로젝트의 실제 태스크 본문
- 특정 프로젝트의 실제 이슈 본문
- L runner 결과
- page 목록
- coverage report 내용
- 프로젝트별 대시보드/보고서 실행 결과

프로젝트 SSoT에 dashboard, task format, issue format, L 기준이 필요하면 0계층에는 실제 프로젝트 산출물을 올리지 않습니다. 0계층은 `setup.sh` 셋업 흐름이나 skill만 제공하고, 생성 결과는 2계층 project SSoT에 둡니다.

프로젝트별 evidence는 coverage 판단 근거이므로 project SSoT 내부에 보존할 수 있습니다. 단, evidence 원본이 제품 소스코드나 대용량 실행 산출물인 경우에는 project SSoT에 위치와 요약을 남기고 원본은 프로젝트 정책에 맞는 외부/로컬 저장 위치에 둡니다.

외부 서비스, 인증 provider, 화면별 QA, DB fixture, runtime harness, L 단계 같은 좁은 실행 처방은 2계층 project SSoT 또는 task 계약에서 관리합니다. 0계층 `system/`은 이 항목을 어떤 판단 근거로 project SSoT에 내려야 하는지와, 통제된 검증과 실제 사용자 경로를 섞지 않는 원칙만 관리합니다.

2계층 project SSoT를 쓰기 전에는 기준 SSoT 위치와 함께 기준 `project/<project-id>` 브랜치, 별도 worktree의 파생 브랜치를 확인합니다. `project/<project-id>` 브랜치가 있으면 그 브랜치에서 판 별도 worktree의 파생 브랜치가 작업 기준입니다. 다른 브랜치에 project SSoT diff가 있으면 바로 이어 쓰지 않고 `기준 아님`, `이관 후보`, `위험`, `사용자 판단 필요`로 분리합니다.

오래된 작업 브랜치의 project SSoT diff를 평가할 때는 비교 기준을 나눕니다. 공통 규칙 drift는 `main-v2` 기준으로 보고, 프로젝트 내부 SSoT의 추가/삭제/이관 여부는 해당 `project/<project-id>` 브랜치 기준으로 봅니다. 최종 트리 차이인 `base..branch`와 브랜치 고유 변경인 `base...branch`를 구분해 보고하고, 둘을 섞어 이관 완료나 삭제 완료로 판단하지 않습니다.

project SSoT 삭제는 이관 또는 폐기 근거가 있는 파일에만 허용합니다. 삭제 대상은 먼저 `이관 확인됨`, `미이관`, `중복`, `폐기 후보`, `사용자 판단 필요`로 분류합니다. `todo`, `in_progress`, active issue, QA evidence, handoff, source doc이 포함된 경우에는 삭제 PR을 만들기 전에 대상 `project/<project-id>` 브랜치나 project SSoT 경로에서 동등한 정보가 살아 있는지 확인합니다.

프로젝트별 shared runtime registry/status도 1계층 project registry/config 또는 2계층 project SSoT에 둡니다. 0계층은 `shared-runtime/<project-id>/<runtime-name>/` 같은 일반 경로 후보, 필드 템플릿, `add-shared-runtime`, `delete-shared-runtime` 규칙만 관리합니다.

## 3계층: Silo Local

3계층은 사일로가 작업 중 임시로 갖는 local 상태입니다.

3계층이 관리하는 것:

- local finding
- local issue/task
- 실험 로그
- 임시 검증 결과
- task가 참조한 shared runtime branch, commit, port, health check 결과
- PR description 초안
- SSoT 승격 후보
- 승격하지 않을 항목

3계층 데이터는 PR 전까지 프로젝트 SSoT에 바로 쓰지 않습니다.

PR 시점에 메인 오케스트레이터가 승격 여부를 판단합니다.

3계층 사일로는 제품 소스코드 저장 위치가 아니라 task 실행 상태를 담는 임시 작업 단위입니다. 사일로 안에 repo clone이 있을 수는 있지만, 그 clone은 해당 task 수행을 위한 폐기 가능한 source workspace이며 사일로 개념 자체와 동일하지 않습니다.

## 승격 규칙

```text
Silo Local
-> PR description
-> Main Orchestrator Review
-> Project Internal Issue/Task
-> 필요 시 0계층 전역 규칙 후보
```

승격할 수 있는 것:

- 반복 가능한 버그
- 프로젝트 전체에 영향을 주는 문제
- 별도 task로 수행 가능한 일
- 프로젝트 전용 skill이 필요한 패턴
- 전역 사용자 취향이나 사일로 운영 규칙에 영향을 주는 피드백

승격하지 않는 것:

- 현재 PR에서 해결된 일회성 문제
- 근거가 약한 추측
- 특정 사일로의 임시 실험 로그
- 재현되지 않은 문제
- 프로젝트 내부에만 의미 있는 정보를 0계층으로 올리는 것

## 프로젝트 자료 커밋 정책

프로젝트 내부 자료는 기본적으로 이 저장소에 커밋하지 않습니다.

기본 원칙:

- 0계층 저장소는 공통 운영 규칙만 커밋합니다.
- 프로젝트 자료는 project repo, fork, `project/*` 브랜치, submodule, external clone, SSoT에 둡니다.
- `project/*` 브랜치는 프로젝트별 정보 보관용 장기 브랜치이며 `main-v2` 병합 대상이 아닙니다.
- 이 저장소 `main-v2`에 프로젝트 자료를 합치려면 왜 코어 저장소에 필요한지 별도 `main-v2` 업데이트 후보로 검토합니다.
- 프로젝트 SSoT의 기본 구조가 반복적으로 필요하다는 요구는 프로젝트 자료 자체가 아니라 0계층 셋업 규칙입니다. 이 경우 root 저장소 `main-v2`에는 `setup.sh` 흐름, 템플릿, repo skill만 추가합니다.

## 메인 오케스트레이터 판단 순서

```text
1. 요청이 0/1/2/3계층 중 어디에 속하는지 판정
2. 0계층이면 system 또는 root skill 수정
3. 1계층이면 project registry/config 수정
4. 2계층이면 해당 project SSoT/fork/submodule에서 처리
5. 3계층이면 silo local로 기록하고 PR까지 유지
6. PR 시점에 승격/비승격 판단
```
