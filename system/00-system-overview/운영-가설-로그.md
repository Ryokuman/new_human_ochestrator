# 운영 가설 로그

## 목적

운영 가설 로그는 0계층에서 관리하는 메타 기록입니다.

여기서 말하는 가설은 프로젝트 제품 가설이 아니라, 에이전트 운영 방식에 대한 가설입니다. 예를 들어 "task를 먼저 만들고 단계별 계획과 pseudo code를 리뷰하면 drift가 줄어든다", "submodule PR을 먼저 평가하고 제품 repo는 pin만 하면 human check 병목이 줄어든다" 같은 작업 방식과 전체 구현 플랜 가정을 기록합니다.

이 로그가 있어야 이전 task 처리 방식과 전체 프로젝트 구현 플랜을 어떤 가정으로 설계했는지, 어떤 정보를 취합해 그 방식을 채택했는지, 결과와 병목이 무엇이었는지 추적할 수 있습니다.

## 기록 단위

하나의 operating hypothesis는 아래 중 하나가 바뀔 때 새로 작성합니다.

- task 처리 순서
- task 작성 방식
- 사일로 생성 방식
- PR review loop 방식
- submodule, monorepo, external clone 같은 repo 운영 방식
- human check 병목을 줄이기 위한 evidence 수집 방식
- 전체 프로젝트 구현 플랜을 수립하는 정보 취합 방식
- 이전 운영 방식에서 발견한 병목을 줄이기 위한 새 접근

단순 프로젝트 기능 요구, 개별 제품 task 원문, 특정 repo의 구현 세부사항은 operating hypothesis가 아닙니다. 그런 내용은 project SSoT, task, issue, PR 본문, 사일로 handoff에 둡니다.

## 저장 위치

운영 가설 원문은 0계층 `system/60-operating-hypotheses/`에 둡니다.

project SSoT에는 project contract와 decision/ADR을 두고, Project Work SSoT에는 프로젝트 내부 task, issue, QA, runbook을 둡니다. project SSoT는 0계층 운영 가설의 적용 결과나 project-specific override를 참조할 수 있지만, 운영 가설의 정본 위치가 아닙니다.

## 필수 항목

각 operating hypothesis에는 최소 아래 항목을 둡니다.

- hypothesis id 또는 이름
- 상태: `draft`, `active`, `closed`, `discarded`
- 시작 날짜와 종료 또는 폐기 날짜
- 운영 가설
- 이 가설을 채택한 이유
- 취합한 정보
- 기존 방식의 문제
- 예상 병목
- 적용한 작업 방식
- 적용 대상 프로젝트 또는 task 범위
- 실행 결과
- 실제로 발견한 병목
- 사람 확인이 필요했던 지점
- 다음 운영 가설에서 유지할 것
- 다음 운영 가설에서 버릴 것
- 반영된 0계층 문서, skill, agent prompt

## Build -> Learn -> Spec 연결

`main-v3/main`의 `Build -> Learn -> Spec`은 제품 코드만의 루프가 아닙니다. 에이전트 운영 방식도 같은 흐름으로 개선합니다.

```text
운영 가설을 세운다
-> 그 가설로 task 처리 방식과 구현 플랜을 설계한다
-> 실제 task/PR/silo에서 실행한다
-> 결과와 병목을 관찰한다
-> 반복 가능한 개선을 0계층 rule, skill, agent prompt로 승격한다
```

이 기록이 없으면 task가 폐기되거나 PR이 drift됐을 때 "왜 그런 방식으로 진행했는지"와 "어느 운영 가설이 병목을 만들었는지"를 추적할 수 없습니다.

## 금지선

- 운영 가설 로그를 프로젝트 제품 원문 저장소로 쓰지 않습니다.
- 특정 프로젝트의 실제 task 본문, secret, 계정, 운영 데이터는 0계층 운영 가설에 복사하지 않습니다.
- 결과가 실패했더라도 해당 가설을 숨기지 않습니다. 실패한 운영 가설은 다음 가설의 입력입니다.
- 사후 합리화만 남기지 않습니다. 가설, 채택 이유, 예상 병목을 먼저 쓰고 실행 결과를 뒤에 붙입니다.
