# 전체 시스템 개요

## 목적

이 시스템의 목적은 사용자가 직접 매번 지시하지 않아도, 사용자와 같은 취향과 판단 기준을 가진 에이전트 시스템이 대상 workspace의 코드를 지속적으로 고도화하는 것입니다.

이 문서는 특정 프로젝트에만 묶이지 않는 공통 설계입니다. 실제 프로젝트명, 레포 경로, 계정, 시크릿, 회사 내부 도구 세부값은 프로젝트별 SSoT 또는 gitignore된 로컬 자료에 둡니다.

에이전트 시스템은 다음을 반복합니다.

```text
기능 시연
-> QA
-> 버그/개선점 발견
-> 이슈/태스크 생성
-> 동적 사일로 생성
-> 사일로가 수정
-> 사일로 내부 검증과 PR 전 리뷰 gate
-> PR 생성
-> 메인 오케스트레이터 리뷰
-> 유저 피드백 반영
-> User Layer evidence와 SSoT 승격 후보 갱신
```

`main-v3/main`에서는 이 루프를 탐색형 제품 엔지니어링 흐름으로 바꿔 운영합니다.

```text
가장 가능성 높은 해석으로 빠른 build
-> 실제 사용/시연
-> 문제와 불확실성 관찰
-> 배운 내용을 task/issue/spec 후보로 승격
-> 필요한 부분만 다음 build 계약으로 정리
```

task 처리 방식, 전체 구현 플랜 수립 방식, 정보 취합 방식, 사일로/PR/review loop 운영 방식이 바뀌는 경우에는 0계층 운영 가설을 남깁니다. 이 기록은 어떤 가설로 작업 방식을 설계했는지, 왜 그 방법을 채택했는지, 실제 task/PR/silo에서 어떤 결과와 병목이 나왔는지 추적하기 위한 것입니다. 자세한 기준은 [`운영-가설-로그.md`](운영-가설-로그.md)를 기준으로 봅니다.

`main`은 레거시 보존 브랜치입니다. 목표 0계층 계층 메인 브랜치는 `main-v3/main`이고, 현재 마이그레이션 전 호환 작업 기준은 `main-v3/main`입니다. PR 생성 시에는 계층별 target/base를 먼저 판정합니다. 0계층 공통 변경은 목표 모델에서 `main-v3/main`, 현재 호환 상태에서 `main-v3/main` 대상 PR로 올립니다. project 계층 변경은 목표 모델에서 `project-{projectName}/main`을 기준 브랜치로 삼되 `project-{projectName}/<branch-name>` 작업 브랜치에서 커밋한 뒤 `project-{projectName}/main` 대상 PR로 올립니다. 현재 호환 상태에서는 `project-{projectName}`와 `project-{projectName}-<branch-name>`을 사용합니다. 기존 slash 기반 `project/<project-id>` 브랜치 모델은 전환/호환 필요 항목으로 다룹니다. Codex PR 리뷰를 기본 gate로 두며 `Build -> Learn -> Spec`을 우선합니다.

## 핵심 구성

| 구성 | 역할 |
|---|---|
| SSoT | 상태, 규칙, 태스크, 이슈의 원본. 단, 사용자별 `personality`, `feedback evidence`, `hypothesis` 실제 상태는 User Layer가 소유하며, `main-v3/main`은 schema, template, 승격 기준만 제공한다. |
| 메인 오케스트레이터 | SSoT를 읽고 갱신하며 전체 태스크/이슈/사일로를 관리 |
| 동적 사일로 | 특정 이슈나 태스크를 맡아 자기 선에서 최대한 해결하는 임시 작업 단위 |
| PR 리뷰 루프 | 사일로가 자체 검증을 거친 뒤 계층별 target/base에 맞춰 PR을 올리고, Codex PR 리뷰 gate를 거치며, 메인이 리뷰하고 필요하면 다시 사일로에 피드백 |
| 유저 피드백 루프 | 실제 사용자가 PR/코드 결과를 보고 준 피드백을 User Layer evidence로 남기고, 승인된 반복 기준만 SSoT와 공통 규칙 후보로 승격 |

## SSoT와 메인 오케스트레이터의 관계

SSoT는 메인 오케스트레이터 그 자체가 아닙니다.

```text
SSoT = 상태와 규칙의 원본
메인 오케스트레이터 = SSoT를 읽고 판단하고 갱신하는 운영 주체
```

메인 오케스트레이터는 SSoT를 기반으로 다음을 결정합니다.

- 어떤 이슈가 중요한가
- 어떤 태스크를 지금 실행할 것인가
- 어떤 사일로를 만들 것인가
- 사일로 결과를 메인 태스크/이슈로 승격할 것인가
- 사용자 피드백을 User Layer evidence로 둘 것인가, 승인된 공통 규칙 또는 사일로 전용 규칙 후보로 승격할 것인가

## 현재 SSoT 적용 단계

SSoT는 필요하지만, 현재 `main-v3/main`에서는 모든 것을 한 번에 통일하기 전까지 강한 실행 의존성으로 두지 않습니다. 또한 현재 `my_ochestrator`의 `main-v3/main`에는 실제 프로젝트 실데이터가 없습니다. 1계층 Project SSoT와 2계층 Project Work SSoT는 실제 프로젝트가 시작된 뒤 생성되는 운영 자료이며, root `system/`은 그 구조와 분리 원칙만 정의합니다.

현재 단계의 SSoT 역할:

- 계층과 저장 위치를 헷갈리지 않게 하는 기준
- 프로젝트 내부 원문을 root `main-v3/main`에 올리지 않게 하는 guard
- 사일로/PR/피드백에서 발견한 반복 규칙을 어디로 승격할지 판단하는 기준
- 나중에 Project SSoT와 Project Work SSoT 구조를 통일할 때 사용할 스키마 초안

현재 단계에서 하지 않는 것:

- 모든 task/issue/QA를 지금 당장 하나의 SSoT로 강제 통합
- SSoT가 완성될 때까지 build나 실험을 중단
- 프로젝트별 실제 원문을 root `main-v3/main`에 복사
- task/issue/QA/runbook/coverage 원문을 1계층 Project SSoT 기준 정보와 섞어 저장
- 아직 확정되지 않은 사용자 취향이나 hypothesis 실제 상태를 public 0계층 전역 규칙으로 즉시 고정

따라서 `main-v3/main`에서는 먼저 작게 만들고, 작업 중 발견한 문제와 반복 패턴을 feedback/follow-up 후보로 남깁니다. 전체 구조가 안정되면 `system/10-ssot/`의 스키마와 project SSoT 생성 도구를 기준으로 통일합니다.

## User Layer와 역할별 취향 갱신

사용자별 `personality`, `feedback evidence`, `hypothesis` 실제 상태는 User Layer가 소유합니다. `main-v3/main`은 실제 개인화 데이터를 저장하지 않고, User Layer를 만들고 runtime `AGENTS.md`로 합성하는 schema, template, guard rule만 제공합니다.

같은 사용자라도 역할과 업무 위치에 따라 좋은 판단이 달라질 수 있습니다. 예를 들어 코드 작성자, 테스트 작성자, QA 에이전트, PR 리뷰어, task 작성자, 사일로 관리자에게 필요한 취향은 서로 다릅니다.

따라서 취향은 아래처럼 나누어 다룹니다.

| 범위 | 의미 | 예시 |
|---|---|---|
| User Layer 전역 규칙 | 모든 작업에 적용되는 사용자별 기본 성향과 금지선 | 한국어 우선, 보호 브랜치 직접 push 금지, 빠른 build 선호 |
| 역할별 프로필 | 특정 에이전트 역할에서만 강해지는 취향 | test-coder의 경계값 테스트, code-coder의 반복 제거, qa-agent의 agent-browser 증거 |
| 프로젝트별 override | 특정 프로젝트에서만 적용되는 작업 방식 | Dynamos page lifecycle, dynaVite runtime, 특정 보호 브랜치 |
| 피드백 이력 | 어떤 피드백이 언제 어떤 범위로 승격됐는지 | 단일 피드백, 반복 피드백, 명시 승인 여부 |

취향 갱신 흐름:

```text
작업 수행
-> 사용자의 직접 피드백 또는 반복되는 review/QA 결과 발견
-> 현재 PR/사일로 수정이 필요한지 먼저 판단
-> User Layer, 역할별 agent prompt, 프로젝트별 override 중 적용 범위 분류
-> 증거 등급 기록
-> 후보 문서 또는 PR 본문에 feedback/follow-up 후보로 남김
-> 사용자 승인 후 반복 가능한 공통 기준만 0계층 작업 브랜치에서 system 문서 또는 skill 초안에 반영
-> setup.sh, runtime AGENTS 합성, 역할별 agent prompt가 새 기준을 읽을 수 있게 연결
```

중요한 기준:

- 단일 작업 피드백을 곧바로 “불변성”으로 고정하지 않습니다.
- 실제 사용자별 취향과 hypothesis 활성 상태는 User Layer에 두고, 역할별로 반복 적용되는 공통 기준만 해당 agent prompt 또는 역할별 후보 문서에 둡니다.
- project contract, 기능/사용자 흐름별 요구사항, decision/ADR, runtime/DB/API/auth 참조는 1계층 Project SSoT에 두고, 그 요구사항을 구현하기 위한 task/issue/QA/runbook/coverage는 2계층 Project Work SSoT에 둡니다.
- 프로젝트별 규칙은 Project SSoT 또는 Project Work SSoT에 두고, 반복 가능한 운영 규칙만 0계층으로 승격합니다.
- 이미 작성된 `system/10-agents/ryokuman-code-coder-prompt.md`, `system/10-agents/ryokuman-test-coder-prompt.md` 같은 문서는 역할별 prompt 보강 근거입니다.
- public 0계층에는 실제 사용자 프로필 파일을 두지 않고, 확정된 공통 schema와 합성 규칙만 AGENTS, 역할별 agent prompt, 피드백 루프 문서에 반영합니다.

## 사일로의 의미

사일로는 고립된 기억 저장소가 아닙니다.

사일로는 특정 이슈나 태스크를 해결하기 위해 동적으로 만들어지는 작업 공간입니다.

좋은 구조:

```text
SSoT 공유
메인 오케스트레이터가 전체 상태 관리
사일로는 특정 태스크만 담당
PR과 보고서로 결과 반환
```

나쁜 구조:

```text
사일로가 각자 다른 판단 기준 보유
사일로가 자기 이슈를 SSoT와 동기화하지 않음
사일로 결과가 PR 외부에 흩어짐
사용자 피드백이 사일로 내부에만 남음
```

## 기본 루프

1. 메인 오케스트레이터가 SSoT를 읽습니다.
2. agent-browser로 실제 기능을 시연하거나 QA 대상을 정합니다.
3. QA 결과에서 버그와 개선점을 추출합니다.
4. 이슈/태스크를 생성하거나 기존 항목에 연결합니다.
5. 실행 가능한 단위마다 사일로를 생성합니다.
6. 사일로는 별도 브랜치에서 최대한 수정하고 검증합니다.
7. PR 생성 전 현재 브랜치의 0계층/project 계층을 판정합니다. 목표 모델에서 0계층은 `main-v3/main`, project 계층은 `project-{projectName}/<branch-name>` 작업 브랜치에서 커밋한 뒤 해당 `project-{projectName}/main` 대상으로 PR을 올립니다. 현재 호환 상태에서는 0계층은 `main-v3/main`, project 계층은 `project-{projectName}-<branch-name>` 작업 브랜치와 `project-{projectName}` 대상 PR을 사용합니다. 두 계층이 섞이면 worktree와 브랜치를 분리합니다. 1계층 Project SSoT와 2계층 Project Work SSoT도 기준 project 브랜치에 직접 커밋하지 않고, project 작업 브랜치와 project 대상 PR을 거칩니다. 기존 slash 기반 `project/<project-id>` 브랜치가 남아 있으면 전환/호환 상태를 확인한 뒤 사용합니다.
8. PR 생성 직후 Codex PR 리뷰 gate를 실행합니다. 최신 리뷰 호출 뒤 3분 동안 `eyes` 반응이 없으면 접수 실패로 보고 같은 head 기준으로 최대 3회까지 재호출하고, 재호출 뒤에는 새 호출 댓글 기준으로 다시 확인합니다. 3회 모두 접수되지 않으면 `Codex 리뷰 접수 실패 timeout`으로 중단합니다. `eyes` 반응을 확인한 뒤 15분 동안 응답이 없으면 `Codex 리뷰 응답 대기 timeout`으로 중단해 이유를 남깁니다. codex-review pass 응답이 아니면 타당한 지적을 수정, 검증, push한 뒤 재리뷰를 요청합니다.
9. 사일로는 PR을 올립니다.
10. PR description에 수정 내용, 검증, 리뷰 gate 결과, 승격 후보, 비승격 항목을 적습니다.
11. 메인 오케스트레이터가 PR을 리뷰합니다.
12. 문제가 있으면 사일로에 재작업을 요청합니다.
13. 머지 시점에 SSoT로 승격할 데이터와 버릴 데이터를 확정합니다.
14. 사용자 피드백이 있으면 메인 규칙 또는 사일로 전용 규칙으로 반영합니다.

## 현재 설계에서 가장 중요한 원칙

- 실제 기능 시연과 QA를 우선합니다.
- `main-v3/main`에서는 완벽한 설계보다 사용 가능한 첫 결과물을 우선합니다.
- `main-v3/main`에서는 질문이 남아도 저위험 변경은 합리적 가정으로 먼저 만들고, 틀린 부분을 학습 결과로 승격합니다.
- SSoT는 필요하지만 현재는 통합 이후 강해질 기준으로 보고, build를 막는 선행 완성 조건으로 두지 않습니다.
- 버그와 태스크를 분리합니다.
- 사일로는 독립 작업자지만, SSoT에 종속됩니다.
- PR은 단순 코드 제출물이 아니라 SSoT 갱신 판단 시점입니다.
- 사용자 피드백은 작업 결과 수정뿐 아니라 에이전트 성향 갱신에도 사용합니다.
- 모든 사람이 읽는 산출물과 프롬프트는 한국어를 우선합니다.
