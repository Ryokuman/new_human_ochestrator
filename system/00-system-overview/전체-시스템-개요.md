# 전체 시스템 개요

## 목적

이 시스템의 목적은 사용자가 직접 매번 지시하지 않아도, 사용자와 같은 취향과 판단 기준을 가진 에이전트 시스템이 대상 workspace의 코드를 지속적으로 고도화하는 것입니다.

이 문서는 특정 프로젝트에만 묶이지 않는 공통 설계입니다. 실제 프로젝트명, 레포 경로, 계정, 시크릿, 회사 내부 도구 세부값은 프로젝트별 SSoT 또는 gitignore된 로컬 자료에 둡니다.

에이전트 시스템은 다음을 반복합니다.

```text
기능 시연
-> QA
-> 버그/개선점 발견
-> 이슈/태스크 생성
-> 동적 사일로 생성
-> 사일로가 수정
-> 사일로 내부 검증과 PR 전 CodeRabbit 자동 리뷰
-> PR 생성
-> 메인 오케스트레이터 리뷰
-> 유저 피드백 반영
-> SSoT와 퍼스널리티 규칙 갱신
```

## 핵심 구성

| 구성 | 역할 |
|---|---|
| SSoT | 상태, 규칙, 태스크, 이슈, 사용자 취향의 원본 |
| 메인 오케스트레이터 | SSoT를 읽고 갱신하며 전체 태스크/이슈/사일로를 관리 |
| 동적 사일로 | 특정 이슈나 태스크를 맡아 자기 선에서 최대한 해결하는 임시 작업 단위 |
| PR 리뷰 루프 | 사일로가 PR 전 CodeRabbit 자동 리뷰와 자체 검증을 거친 뒤 PR을 올리고, 메인이 리뷰하며 필요하면 다시 사일로에 피드백 |
| 유저 피드백 루프 | 실제 사용자가 PR/코드 결과를 보고 준 피드백을 SSoT와 퍼스널리티 규칙에 반영 |

## SSoT와 메인 오케스트레이터의 관계

SSoT는 메인 오케스트레이터 그 자체가 아닙니다.

```text
SSoT = 상태와 규칙의 원본
메인 오케스트레이터 = SSoT를 읽고 판단하고 갱신하는 운영 주체
```

메인 오케스트레이터는 SSoT를 기반으로 다음을 결정합니다.

- 어떤 이슈가 중요한가
- 어떤 태스크를 지금 실행할 것인가
- 어떤 사일로를 만들 것인가
- 사일로 결과를 메인 태스크/이슈로 승격할 것인가
- 사용자 피드백을 전역 규칙으로 반영할 것인가, 사일로 전용 규칙으로 둘 것인가

## 사일로의 의미

사일로는 고립된 기억 저장소가 아닙니다.

사일로는 특정 이슈나 태스크를 해결하기 위해 동적으로 만들어지는 작업 공간입니다.

좋은 구조:

```text
SSoT 공유
메인 오케스트레이터가 전체 상태 관리
사일로는 특정 태스크만 담당
PR과 보고서로 결과 반환
```

나쁜 구조:

```text
사일로가 각자 다른 판단 기준 보유
사일로가 자기 이슈를 SSoT와 동기화하지 않음
사일로 결과가 PR 외부에 흩어짐
사용자 피드백이 사일로 내부에만 남음
```

## 기본 루프

1. 메인 오케스트레이터가 SSoT를 읽습니다.
2. agent-browser로 실제 기능을 시연하거나 QA 대상을 정합니다.
3. QA 결과에서 버그와 개선점을 추출합니다.
4. 이슈/태스크를 생성하거나 기존 항목에 연결합니다.
5. 실행 가능한 단위마다 사일로를 생성합니다.
6. 사일로는 별도 브랜치에서 최대한 수정하고 검증합니다.
7. 일반 사일로는 PR 생성 전 CodeRabbit CLI 리뷰를 기본 gate로 실행하고, 생략 또는 실패 시 이유를 남깁니다.
8. 사일로는 PR을 올립니다.
9. PR description에 수정 내용, 검증, CodeRabbit 자동 리뷰 결과, 승격 후보, 비승격 항목을 적습니다.
10. 메인 오케스트레이터가 PR을 리뷰합니다.
11. 문제가 있으면 사일로에 재작업을 요청합니다.
12. 머지 시점에 SSoT로 승격할 데이터와 버릴 데이터를 확정합니다.
13. 사용자 피드백이 있으면 메인 규칙 또는 사일로 전용 규칙으로 반영합니다.

## 현재 설계에서 가장 중요한 원칙

- 실제 기능 시연과 QA를 우선합니다.
- 버그와 태스크를 분리합니다.
- 사일로는 독립 작업자지만, SSoT에 종속됩니다.
- PR은 단순 코드 제출물이 아니라 SSoT 갱신 판단 시점입니다.
- 사용자 피드백은 작업 결과 수정뿐 아니라 에이전트 성향 갱신에도 사용합니다.
- 모든 사람이 읽는 산출물과 프롬프트는 한국어를 우선합니다.
