# 버전 가설 로그

## 목적

버전 가설 로그는 특정 제품 또는 운영 버전이 어떤 가설로 설계되었고, 그 가설에 따라 무엇을 만들었으며, 결과와 병목이 무엇이었는지 기록하는 project-level 운영 장치입니다.

task 내부 `hypothesis_chain`은 실행 중 실패와 재시도 가설을 다룹니다. 버전 가설 로그는 그보다 상위에서 "이번 버전은 어떤 판단으로 이런 프로그램을 설계했는가"를 다룹니다.

## 기록 단위

하나의 version hypothesis는 아래 중 하나가 바뀔 때 새로 작성합니다.

- 제품 또는 운영 버전의 핵심 설계 가설
- 완료 경로 또는 사용자 가치 가정
- 사일로 운영 방식, 검증 방식, submodule/monorepo 같은 구조 가정
- human check 병목을 줄이기 위한 자동화 가정
- 이전 버전 결과에서 발견한 병목을 해결하기 위한 접근

단순 버그 수정, 문구 수정, 단일 PR 리뷰 대응은 새 version hypothesis가 아닙니다. 그런 내용은 task, issue, PR 본문, task 내부 `hypothesis_chain`에 둡니다.

## 필수 항목

각 version hypothesis에는 최소 아래 항목을 둡니다.

- version id 또는 이름
- 시작 날짜와 종료 또는 폐기 날짜
- 설계 가설
- 이 가설을 채택한 이유
- 예상 병목
- 실행한 task, issue, silo, PR
- 만들어진 결과물
- 검증 evidence
- 실제로 발견한 병목
- 사람 확인이 필요했던 지점
- 다음 버전에서 유지할 것
- 다음 버전에서 버릴 것
- 후속 task/spec/SSoT 후보

## 계층과 저장 위치

0계층 `system/`에는 버전 가설 로그의 형식, 승격 기준, 금지선만 둡니다.

프로젝트별 실제 version hypothesis 원문은 해당 project SSoT에 둡니다. project SSoT가 없으면 먼저 project SSoT 위치를 정하고, 임시로 root `main-v2`에 프로젝트 버전 가설 원문을 커밋하지 않습니다.

3계층 사일로는 자기 실행 결과를 PR 본문이나 handoff에 요약할 수 있지만, 버전 가설의 정본은 project SSoT입니다.

## Build -> Learn -> Spec 연결

`main-v2`에서는 먼저 build하고 배운 내용을 spec으로 승격합니다. 이때 version hypothesis는 아래 질문에 답해야 합니다.

```text
어떤 가설상으로 이 버전을 설계했는가?
그 가설 때문에 어떤 작업 순서와 구조를 선택했는가?
실제로 나온 결과물은 무엇인가?
어떤 병목이 드러났는가?
다음 버전에서 무엇을 바꿀 것인가?
```

이 기록이 없으면 여러 task가 완료되어도 "왜 이런 방향으로 왔는지"와 "어느 병목 때문에 다음 설계가 바뀌었는지"를 추적할 수 없습니다.

## 금지선

- 버전 가설 로그를 사후 합리화 문서로 쓰지 않습니다. 가설, 기대 결과, 예상 병목을 먼저 적고 실행 결과를 뒤에 붙입니다.
- 최종 결과가 성공처럼 보여도 중간 병목을 숨기지 않습니다.
- 사람 확인 병목을 단순히 "사용자 확인 필요"로 끝내지 않고, agent가 다음 버전에서 줄일 수 있는 증거 수집, pseudo code review, E2E, DB query, screenshot, PR review gate 후보로 분리합니다.
- 프로젝트 내부 실제 task 원문, secret, 계정, 운영 데이터는 0계층 버전 가설 문서에 복사하지 않습니다.
