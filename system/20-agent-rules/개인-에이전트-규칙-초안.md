# 개인 에이전트 규칙 초안

작성 기준: 2026-06-09

## 목적

이 문서는 사용자 분석과 취향 불변성 후보를 실제 에이전트 행동 규칙으로 바꾼 초안입니다.

아직 `AGENTS.md`, `CLAUDE.md`, `SKILL.md`에 반영하지 않았습니다. 검토 후 승격할 후보입니다.

## 핵심 원칙

### 1. 목표 유형 먼저 분리

사용자가 "레포 파악", "디렉토리 파악", "셋업", "이 프로젝트 설명"을 요청하면, 먼저 작업 목적을 아래 세 갈래로 구분합니다.

| 유형 | 의미 | 산출물 |
|---|---|---|
| 제품/코드 작업 | 실제 버그 수정, 기능 구현, 테스트 통과 | 코드 diff, test, PR |
| 사용자/작업 방식 분석 | 사용자가 무엇을 하려 했는지, 어떤 성향인지 분석 | work map, personality profile, invariants |
| 에이전트 셋업 생성 | 개인 에이전트 프롬프트, skill, AGENTS.md/CLAUDE.md 생성 | 규칙 초안, 프롬프트 초안, skill 초안 |

목표가 모호하면 바로 코드 수정으로 넘어가지 않습니다. 먼저 현재까지의 산출물이 어느 유형인지 분류합니다.

### 2. 사용자 분석 목표에서는 코드 수정 금지

사용자 목표가 "퍼스널리티", "취향 불변성", "기계인간", "에이전트 셋업"이면 제품 코드 수정은 중심 작업이 아닙니다.

이 경우:

- 코드 이슈는 부수 발견으로 기록합니다.
- 승인 문구를 반복해서 요구하지 않습니다.
- 다음 산출물은 사용자 분석 문서 또는 에이전트 규칙 문서여야 합니다.

### 2-1. 사일로 실행 목표에서는 격리 수정 허용

사용자 목표가 사일로를 통한 문제 해결이면, source code 수정 자체를 명시 승인 대기로 묶지 않습니다.

사일로 기본 규칙:

- 필요한 레포지토리만 새로 clone합니다.
- 보호 브랜치에서 직접 작업하지 않습니다.
- 항상 새 작업 브랜치를 생성합니다.
- 기본 실행 모드는 `yolo`입니다.
- 격리 clone 내부에서는 source code, generated output, test, tooling을 승인 없이 자유롭게 수정할 수 있습니다.
- 수정이 실패하거나 코드가 크게 망가지면 해당 clone/branch를 폐기할 수 있습니다.
- 결과는 PR로 제출하고, 메인 오케스트레이터가 리뷰합니다.

절대 금지:

- `main`, `dev`, `develop`, `master` 직접 commit 또는 push
- production 데이터 변경
- secret 값 읽기 또는 기록
- force push

### 2-2. main-v2에는 project 산출물이 아니라 생성 시스템을 올림

root 저장소 `main-v2`는 0계층 `system/`만 기준으로 봅니다.

프로젝트별 대시보드, 태스크 형식, 이슈 형식, L 기준, Obsidian Dataview 설정이 필요하면 실제 project SSoT 산출물을 `main-v2`에 직접 커밋하지 않습니다. 대신 `main-v2`에는 이를 생성하는 스크립트, 템플릿, skill 초안만 추가합니다.

예:

- 올릴 것: `system/scripts/create-project-ssot.mjs`
- 올릴 것: `system/20-agent-rules/skill-drafts/projects-setup/SKILL.md`
- 올리지 않을 것: `projects/<project>/02-project-internal/30-tasks/TASK-....md`
- 올리지 않을 것: `projects/<project>/02-project-internal/.obsidian/plugins/...`

Dataview 플러그인이 대시보드 복구에 필요하다는 판단은 맞지만, `main-v2`에는 플러그인을 기본 설치하는 생성 도구와 셋업 스킬만 둡니다.

### 2-3. 에이전트 md는 reference 기반으로 보강

사용자가 에이전트 md, AGENTS.md, CLAUDE.md, 프롬프트, skill이 빈약하다고 피드백하면 바로 장문 규칙을 추가하지 않습니다.

먼저 `system/20-agent-rules/references/`에 근거를 정리합니다.

- 기존 프로젝트 운영 방식
- PR 리뷰에서 반복된 기준
- 사용자 보고 방식 피드백
- 퍼스널리티 후보와 승인 상태
- 프로젝트 자료를 어디서 읽어야 하는지에 대한 색인

에이전트 md에는 reference의 원문을 복사하지 않고, 언제 어떤 reference를 읽을지와 어떤 기준으로 장기 규칙에 반영할지를 적습니다.

이 규칙은 단일 피드백을 장기 퍼스널리티 규칙으로 과도하게 확정하지 않기 위한 보호 장치입니다.

### 3. 상태 보고는 네 칸으로 분리

큰 작업 보고는 기본적으로 아래 구조를 사용합니다.

```text
완료된 것
아직 안 된 것
목표 밖으로 만들어진 것
다음에 할 것
```

필요하면 여기에 `검증된 것`, `미검증`, `승인 필요`를 추가합니다.

### 4. blocked는 전체 목표 기준으로만 사용

특정 코드 수정이 승인 대기여도, 사용자 분석이나 문서 작업이 계속 가능하면 전체 목표를 blocked로 표시하지 않습니다.

blocked를 쓰기 전에 확인합니다.

1. 현재 목표가 정말 더 진행 불가능한가
2. 다른 산출물로 의미 있는 진척이 가능한가
3. 막힌 것이 제품 코드 갈래인지, 사용자 분석 전체인지

### 5. 취향 불변성은 등급화

사용자 성향을 쓸 때는 아래 등급을 붙입니다.

| 등급 | 사용 조건 |
|---|---|
| 확정 | 사용자 명시 승인 또는 여러 맥락 반복 |
| 강한 후보 | 반복 관찰되고 적용 위험이 낮음 |
| 중간 후보 | 신호는 있으나 더 관찰 필요 |
| 약한 후보 | 단서 수준 |
| 제외 | 제품 이슈 또는 일회성 상황 |

단일 발화에서 바로 "사용자는 항상 X"라고 쓰지 않습니다.

### 6. 관찰과 해석 분리

사용자 분석 문서는 다음 형식을 선호합니다.

```text
관찰:
- 사용자가 실제로 한 말 또는 문서 근거

해석:
- 그 관찰에서 추론되는 성향

에이전트 대응:
- 다음 세션에서 어떻게 행동할지
```

### 7. 토큰 효율 설명

큰 workspace를 다룰 때는 다음을 먼저 설명합니다.

- physical size
- token-relevant source size
- 제외한 디렉토리
- 왜 제외했는지

기본 제외:

- `.git`
- `node_modules`
- `.next`
- `dist`
- `build`
- `target`
- `.cache`
- generated output
- logs
- secrets, `.env`

### 8. 목표 밖 발견은 별도 보관

분석 중 제품 버그나 코드 수정 후보를 발견해도 바로 next action으로 올리지 않습니다.

형식:

```text
부수 발견:
- 항목:
- 왜 목표 밖인지:
- 나중에 처리하려면 필요한 승인:
```

### 9. 사용자가 혼선을 묻는 경우의 답변

사용자가 아래처럼 물으면:

- "제가 잘못 파악했나요"
- "제가 뭘 몰라서 그런 건가요"
- "왜 코드 수정이 필요한가요"

다음 순서로 답합니다.

1. 사용자 이해 부족인지, 에이전트 목표 오해인지 분리
2. 에이전트가 잘못 좁혔다면 명확히 인정
3. 원래 목표 기준으로 다음 산출물을 재정렬

### 10. 문서 생성 후 검증

Markdown 분석 문서를 만든 뒤에는 최소 검증을 수행합니다.

```bash
rg -n "password|secret|token|api_key|\\.env|<[^>]+>|TODO|TBD|비밀" <new-docs>
rg -n "목표|완료|미완료|취향 불변성|다음" <new-docs>
```

검증 결과:

- 민감정보가 있으면 제거합니다.
- placeholder가 있으면 의도된 예시인지 확인합니다.
- 목표와 다음 행동이 코드 수정으로 drift하지 않았는지 확인합니다.

## 승격 후보 문구

아래 문구는 `AGENTS.md` 또는 `CLAUDE.md`에 넣을 수 있는 압축 버전입니다.

```text
사용자가 레포/디렉토리 파악을 요청할 때는 먼저 목적을 분리한다. 제품 코드 수정, 사용자/작업 방식 분석, 에이전트 셋업 생성은 서로 다른 산출물을 가진다. 사용자 분석 목적이면 코드 수정 후보는 부수 발견으로만 기록하고, work map, personality profile, taste invariants, agent rules를 우선 생성한다.
```

```text
큰 작업 보고는 완료/미완료/목표 밖 산출물/다음 산출물로 나눈다. blocked는 전체 목표가 실제로 막혔을 때만 사용한다.
```

```text
취향 불변성은 확정/강한 후보/중간 후보/약한 후보/제외로 등급화한다. 단일 발화나 특정 제품 이슈를 사용자 불변성으로 바로 승격하지 않는다.
```

```text
사일로는 필요한 레포지토리만 새로 clone하고, 보호 브랜치가 아닌 새 작업 브랜치에서 자유롭게 수정한다. main/dev/develop/master에는 직접 commit/push하지 않는다. 결과는 PR 본문으로 제출하며, SSoT 승격 후보와 승격하지 않을 항목을 반드시 분리한다.
```

```text
root 저장소 `main-v2`에는 프로젝트 내부 SSoT 산출물을 직접 올리지 않는다. 프로젝트 SSoT의 태스크 시스템, 이슈 관리, L 기준, 대시보드가 필요하면 system 아래 생성 스크립트나 skill 초안로 제공하고, 생성 결과는 해당 project SSoT에 둔다.
```

```text
에이전트 md가 빈약하다는 피드백을 받으면 기존 프로젝트 운영 방식, PR 리뷰 반복 피드백, 보고 방식, 퍼스널리티 후보를 references에 먼저 정리한다. 이후 반복 근거와 승인 상태가 확인된 내용만 AGENTS.md, CLAUDE.md, 최종 프롬프트, skill 초안에 반영한다.
```
