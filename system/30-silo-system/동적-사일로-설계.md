# 동적 사일로 설계

## 목적

사일로는 메인 오케스트레이터가 특정 이슈나 태스크를 해결하기 위해 동적으로 만드는 작업 단위입니다.

사일로는 독립적으로 일하지만, SSoT와 메인 오케스트레이터의 규칙을 따릅니다.

## 사일로 입력

사일로가 시작할 때 받는 정보:

- source issue 또는 task
- 허용 scope
- clone 대상 레포지토리
- 공용 서비스 사용 여부
- 기준 브랜치
- 작업 브랜치 이름
- acceptance criteria
- verification plan
- 사용자 취향 규칙
- 승인 경계
- 관련 QA 증거
- execution mode, 기본값은 `yolo`

## 사일로 출력

사일로는 작업 후 다음을 남깁니다.

- 수정 branch
- PR
- 작업 요약
- 검증 결과
- 새로 발견한 local issue/task
- SSoT 승격 후보
- 승격하지 않을 local-only 항목
- 사용자 또는 메인에게 필요한 질문

## 사일로 작업 루프

```text
1. 입력 task/issue 읽기
2. 필요한 레포지토리만 새로 clone
3. 필요한 공용 서비스가 이미 떠 있는지 확인
4. 보호 브랜치에서 새 작업 브랜치 생성
5. 관련 코드와 QA 증거 확인
6. 문제 해결에 필요한 수정과 실험 수행
7. 테스트와 검증
8. agent-browser로 필요한 경우 재시연
9. PR 생성
10. PR description에 결과, 승격 후보, 비승격 항목 기록
11. 메인 리뷰 대기
12. 리뷰 피드백 반영
```

## 사일로 작업 공간 규칙

사일로는 공유 workspace를 직접 더럽히는 장기 작업자가 아닙니다.

기본 원칙:

- 사일로는 그때그때 필요한 레포지토리만 clone합니다.
- clone된 작업 공간은 폐기 가능해야 합니다.
- 사일로는 `main`, `dev`, `develop`, `master` 같은 보호 브랜치에서 직접 작업하지 않습니다.
- 항상 새 작업 브랜치를 생성한 뒤 수정합니다.
- 격리 clone과 작업 브랜치 안에서는 문제 해결에 필요한 코드를 자유롭게 수정할 수 있습니다.
- 코드가 크게 망가져도 해당 clone/branch를 폐기하면 됩니다.
- 최종 결과는 PR로만 메인 오케스트레이터에게 제출합니다.

이 구조에서 안전 장치는 "수정 제한"이 아니라 "격리, 브랜치, PR 리뷰, 폐기 가능성"입니다.

## 공용 서비스

사일로별로 매번 clone하거나 수정하지 않는 공용 서비스가 있을 수 있습니다.

예:

- backend API
- shared DB proxy
- 공용 dev server

공용 서비스 운영 기준:

- 메인 오케스트레이터가 세션 동안 하나만 띄웁니다.
- 사일로는 해당 서비스를 검증 대상으로 사용할 수 있습니다.
- 사일로는 기본적으로 공용 서비스를 직접 clone하거나 수정하지 않습니다.
- 공용 서비스 수정 필요성이 발견되면 PR description에 `SSoT 승격 후보` 또는 `메인 오케스트레이터 판단 필요`로 남깁니다.

## YOLO 모드

사일로 기본 실행 모드는 `yolo`입니다.

`yolo`의 의미:

- 사일로는 수정 전 승인 대기 없이 문제 해결을 우선합니다.
- source code, generated output, test, tooling을 격리 clone 내부에서 자유롭게 수정합니다.
- 접근 가능한 검증 명령과 agent-browser QA를 스스로 실행합니다.
- 실패하거나 방향이 틀리면 해당 clone/branch를 폐기하고 다시 시작할 수 있습니다.
- 완료되면 PR description에 수정 범위, 검증 결과, SSoT 승격 후보, 승격하지 않을 항목을 적습니다.

`yolo`에서도 금지되는 것:

- 보호 브랜치 직접 commit 또는 push
- production 데이터 쓰기
- secret 값 읽기 결과를 로그나 문서에 기록
- 공유 브랜치 force push
- SSoT 전역 규칙을 임의 변경

## 사일로가 "자기가 아는 선"에서 고친다는 의미

사일로는 현재 받은 context와 접근 가능한 도구 안에서 최대한 해결합니다.

하지만 아래 경우에는 무리하게 추측하지 않습니다.

- SSoT와 충돌하는 정보가 있음
- 보호 브랜치 직접 수정, production 데이터 변경, secret 기록처럼 YOLO 금지선 밖 변경이 필요함
- 재현은 됐지만 원인이 명확하지 않음
- 다른 프로젝트와 연쇄 변경이 필요함
- 사용자 취향 규칙과 충돌하는 판단이 필요함

이 경우 PR description 또는 사일로 보고서에 `메인 판단 필요`로 남깁니다.

## 사일로 내부 이슈/태스크

사일로는 작업 중 새 문제를 발견할 수 있습니다.

예:

- 원래 버그를 고치다 보니 다른 화면도 같은 문제를 가짐
- 테스트는 고쳤지만 generated output 정책이 더 넓게 깨져 있음
- 현재 task보다 큰 구조 문제가 발견됨
- 사용자 취향 규칙이 부족해 판단이 흔들림

이 문제들은 바로 메인 SSoT에 쓰지 않고, 우선 사일로 local finding으로 기록합니다.

이후 PR 시점에 승격 후보로 제출합니다.

## 사일로 종료 상태

| 상태 | 의미 |
|---|---|
| `pr-opened` | PR 생성 완료, 메인 리뷰 대기 |
| `needs-rework` | 메인 리뷰 또는 사용자 피드백으로 재작업 필요 |
| `merged` | PR 머지 완료 |
| `blocked` | 사일로 단독으로 해결 불가 |
| `abandoned` | scope 변경 또는 중복으로 폐기 |

## 사일로 생성 원칙

- 사일로는 task/issue 단위로 생성합니다.
- 역할별 사일로가 아니라 작업 단위별 사일로입니다.
- QA, 구현, 리뷰 역할은 사일로 내부 또는 메인 루프에서 호출되는 worker입니다.
- 사일로가 만든 모든 중요한 발견은 PR description을 통해 메인으로 돌아와야 합니다.
- 사일로는 보호 브랜치가 아니라 새 작업 브랜치에서만 수정합니다.
