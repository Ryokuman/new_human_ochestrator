# 동적 사일로 설계

## 목적

사일로는 메인 오케스트레이터가 특정 이슈나 태스크를 해결하기 위해 동적으로 만드는 작업 단위입니다.

사일로는 독립적으로 일하지만, SSoT와 메인 오케스트레이터의 규칙을 따릅니다.

## 사일로 입력

사일로가 시작할 때 받는 정보:

- source issue 또는 task
- 허용 scope
- clone 대상 레포지토리 목록
- 공용 서비스 사용 여부
- 참조할 shared runtime set과 branch/commit/port
- 기준 브랜치
- 작업 브랜치 이름
- acceptance criteria
- verification plan
- criteria별 테스트 계약
- 사용자 취향 규칙
- 승인 경계
- 관련 QA 증거
- execution mode, 기본값은 `yolo`

## 사일로 기본 구조

사일로는 역할 이름이 아니라 작업 단위 이름으로 만든다. 기본 디렉터리 이름은 task면 `task-<TASK-ID>/`, issue면 `issue-<ISSUE-ID>/`, page면 `page-<PAGE-ID>/`를 쓴다.

사용자가 task 실행, 태스크 진행, task 수행을 요청하면 메인 오케스트레이터는 별도 확인 없이 아래 준비 범위를 한 번에 수행한다.

```text
task-xxxx/ 생성
-> goal.md 작성
-> 필요한 repo clone
-> repo별 작업 브랜치 생성
```

이 사일로 디렉토리는 현재 workspace 루트에 만든다. 사용자가 명시하지 않는 한 `/tmp`, 홈 디렉토리, 숨김 디렉토리, 에이전트 전용 임시 경로에 만들지 않는다.

예:

```text
task-0055/
  goal.md
  <repo-a>/
  <repo-b>/
  artifacts/
  logs/
  reports/
```

사일로 루트와 제품 repo/source workspace는 구분합니다. 사일로 루트는 task 실행 단위의 컨테이너이고, 제품 repo는 그 사일로가 필요할 때 clone하거나 연결하는 별도 작업 대상입니다.

따라서 사일로는 소스코드 자체가 아닙니다. 사일로에는 `goal.md`, 로그, 검증 결과, 임시 산출물, PR 전 상태가 남고, 실제 제품 소스코드는 별도 repo/worktree 또는 gitignore된 source 위치를 기준으로 다룹니다.

사일로 루트 안에는 해당 작업에 필요한 레포지토리만 clone한다. 프로젝트 설정이나 task가 `generator`, `runtime`, `frontend`, `backend` 같은 repo set을 지정하면 그 목록을 따른다. 공용 backend처럼 메인 오케스트레이터가 세션 동안 하나만 관리하는 서비스는 기본 clone 대상에서 제외한다.

여러 task silo가 함께 참조하는 장기 runtime checkout은 shared runtime으로 분리한다. 기본 경로 후보는 workspace root 기준 `shared-runtime/<project-id>/<runtime-name>/`이다. shared runtime은 task silo가 직접 소유하지 않는 공용 실행 repo 묶음이며, 프로젝트별 구성이 다르다. 어떤 프로젝트는 backend와 frontend를 함께 쓰고, 어떤 프로젝트는 worker, DB emulator, external service mock, generator repo 조합을 쓸 수 있다.

page-lifecycle, run, E2E처럼 runtime 상태가 검증 전제가 되는 사일로는 시작 전에 `shared-runtime-health-check`를 사용한다. 대상 프로젝트의 `runtime_set`이 없으면 lifecycle을 시작하지 않고, `add-shared-runtime` 또는 project runtime_set 정의가 먼저 필요하다고 보고한다. `runtime_set`에 서버형 runtime이 있으면 health command, URL, port, env policy를 확인하고, 실패 시 lifecycle을 중단한다. 서버형 runtime이 없으면 health check를 생략할 수 있지만 생략 이유를 `goal.md`나 보고서에 남긴다.

각 레포지토리는 clone 직후 기준 브랜치를 확인하고, 보호 브랜치가 아닌 새 작업 브랜치를 만든다. 같은 task 사일로에 들어온 여러 레포지토리는 같은 task id를 포함한 브랜치 이름을 쓰되, PR 필요 여부는 레포지토리별 diff와 완료 결과를 기준으로 따로 판단한다.

## 사일로 유형

사일로는 산출물 성격에 따라 `테스트 사일로`와 `일반 사일로`로 구분한다. 이 구분은 특정 프로젝트 전용 규칙이 아니라 여러 프로젝트에 적용하는 0계층 생명주기 규칙이다.

| 유형 | 주 산출물 | 대표 용도 | 기본 정리 기준 |
|---|---|---|---|
| 테스트 사일로 | 개별 보고서, evidence, 전체 사일로 보고서, Issue/Task 승격 후보 | lifecycle 테스트, e2e 검증, runtime 검증, 탐색 검증 | 보고서와 evidence 승격 gate 통과 후 삭제 가능 |
| 일반 사일로 | 변경 diff, PR, patch, 검증 증거, handoff | 구현, 수정, 문서, repair, conflict, PR 작업 | PR/patch 대응 관계와 작업트리 상태 확인 후 보존 또는 정리 |

테스트 사일로는 보고서가 주 산출물인 임시 실행 환경이다. 테스트 종료 뒤 개별 보고서를 남기고, 보고서와 evidence가 project SSoT 또는 지정 위치에 승격됐는지 확인한 뒤 사일로 디렉터리를 삭제할 수 있다.

일반 사일로는 변경/PR/patch/evidence가 주 산출물인 작업 환경이다. 테스트 사일로의 자동 삭제 규칙을 일반 사일로에 적용하지 않는다. 일반 사일로 정리는 PR 머지 여부, patch 대응 관계, 미커밋 변경, 원격 상태, worktree 상태를 확인한 뒤 별도로 판단한다.

## 테스트 사일로 생명주기

테스트 사일로는 아래 순서로 다룬다.

```text
1. 준비: goal, 대상, runtime 또는 shared runtime, 금지선, report 위치를 명시한다.
2. 실행: lifecycle/e2e/runtime/탐색 검증을 수행하고 evidence를 수집한다.
3. 종료: 개별 보고서를 작성하고 evidence/보고서가 SSoT 또는 지정 위치로 승격됐는지 확인한다.
4. 삭제: 보고서 승격 gate와 dirty status 확인을 통과한 뒤 사일로 디렉터리를 삭제할 수 있다.
5. batch 종료: 개별 테스트 사일로 보고서를 묶어 전체 사일로 보고서를 작성하고 반복 원인을 추출한 뒤 Issue/Task 생성 후보를 만든다.
```

테스트 사일로 삭제 전 gate:

- 개별 보고서가 작성되어 있어야 한다.
- evidence 원본 또는 요약 위치가 project SSoT, report 저장소, 또는 사용자가 지정한 위치에 남아 있어야 한다.
- 보고서에는 대상, 실행 조건, 사용한 runtime/shared runtime, 실패/성공 결과, 반복 원인 후보, Issue/Task 승격 후보가 있어야 한다.
- 삭제 전 사일로 루트와 내부 repo의 dirty status를 확인해야 한다.
- destructive action, upload/import, production mutation은 테스트 사일로라도 별도 승인이 필요하다.

테스트 사일로 batch 종료 시에는 개별 보고서를 그대로 합치는 데서 멈추지 않고, 반복 원인과 중복 증거를 정리한다. 전체 사일로 보고서는 `개별 보고서`, `전체 사일로 보고서`, `Issue/Task 승격 후보`, `삭제된 사일로`를 분리해 보고한다.

## 일반 사일로 생명주기

일반 사일로는 자동 삭제를 기본값으로 삼지 않는다. 구현, 수정, 문서, repair, conflict, PR 작업은 사일로 디렉터리와 내부 clone이 후속 확인 근거가 될 수 있으므로 아래 확인 뒤 정리한다.

- PR이 있으면 PR URL, state, merge 상태, merge commit, head branch를 확인한다.
- patch 제출이면 patch가 어떤 branch/commit/PR과 대응되는지 확인한다.
- 내부 repo와 사일로 루트의 미커밋 변경, untracked 파일, ahead commit, 원격 push 상태를 확인한다.
- worktree가 연결되어 있으면 clean 상태와 연결 branch를 확인한다.
- repair/conflict 사일로는 원 PR, 대체 PR, 또는 patch 동등성이 확인되기 전까지 삭제하지 않는다.
- 정리 보고에는 `PR/patch`, `검증`, `merge/cleanup 상태`, `보존/삭제 후보`를 분리한다.

`goal.md`에는 아래 항목을 담는다.

- 원래 task/issue 목표와 SSoT 경로
- 사일로 유형: 테스트 사일로 또는 일반 사일로
- 필요한 repo 목록
- 참조한 shared runtime set, branch, commit, port, health check 결과
- 테스트 사일로인 경우 report 위치와 batch 묶음 기준
- 보호 브랜치와 권장 작업 브랜치명
- 사일로 내부 개발자/QA/리뷰 역할의 책임
- 금지선: secret 기록, production 데이터 쓰기, 보호 브랜치 직접 push, 승인 없는 data SSoT 수정
- 검증 기준
- 원본 task의 Output, Acceptance Criteria, Test Plan
- Dynamos 사일로에서 브라우저 확인이 필요한 경우 `agent-browser`로만 확인한다는 기준
- PR 본문 필수 항목

shared runtime 자체 변경이 필요하면 현재 task silo의 제품 코드 PR에 섞지 않고 별도 task, branch, PR로 분리한다. task silo는 자신이 참조한 shared runtime의 workspace path, branch, commit, port, env policy, health check 결과만 `goal.md`, handoff, PR 본문에 남긴다. env policy에는 파일 경로나 secret provider 정책만 쓰고 secret 값은 기록하지 않는다.

개발 세션에는 상세 지시를 다시 풀어 쓰지 않는다. 해당 사일로 디렉토리에서 `/goal`로 `goal.md 달성 부탁해` 수준의 짧은 요청만 전달한다. 세부 실행 계약은 `goal.md`가 단일 기준이다.

`goal.md`는 원본 task의 `Output`과 `Acceptance Criteria`를 완료 기준으로 삼아야 한다. 각 criteria는 `unit`, `runner`, `E2E`, `agent-browser`, `manual` 중 하나 이상의 검증 방법과 연결한다. 화면 동작이 바뀌는 task는 E2E 또는 `agent-browser` 증거를 우선하고, 신규/변경 로직은 가능한 범위에서 unit test를 추가한다. 측정 가능한 repo에서는 신규/변경 코드의 coverage를 우선 확인하며, 전체 90% coverage는 프로젝트가 측정 범위와 적용 시점을 정한 뒤 단계적으로 강제한다.

## 사일로 출력

사일로는 작업 후 다음을 남깁니다.

- 사일로 유형
- 수정 branch 목록
- 필요한 레포지토리별 PR
- 테스트 사일로인 경우 개별 보고서, evidence 위치, 삭제 가능 여부
- 테스트 사일로 batch 종료인 경우 전체 사일로 보고서와 Issue/Task 승격 후보
- 작업 요약
- 검증 결과
- criteria별 검증 결과
- 새로 발견한 로컬 issue/task
- SSoT 승격 후보
- 승격하지 않을 로컬 전용 항목
- 사용자 또는 메인에게 필요한 질문

## 사일로 내부 역할

하나의 사일로는 최소 세 역할을 가진다.

| 역할 | 책임 |
|---|---|
| 개발자 에이전트 | task/issue를 구현하고, 필요한 repo branch와 diff를 만든다. |
| QA 에이전트 | acceptance criteria 기준으로 unit, runner, E2E, agent-browser, report, 회귀 여부를 검증한다. |
| 리뷰 에이전트 | scope, branch safety, secret/protected branch 위반, PR 본문, SSoT 승격 후보를 검토한다. |

세 역할은 별도 사일로가 아니다. 같은 task 사일로 안에서 순차 또는 병렬 worker로 호출된다. 구현 중간에 사용자의 세부 승인을 기다리지 않는 것이 기본이며, 사용자 승인이 필요한 경우는 protection/secret/production/data policy 같은 사일로 금지선에 닿을 때로 제한한다.

## 사일로 작업 루프

```text
1. 입력 task/issue 읽기
2. 현재 workspace 루트에 `<unit-id>/` 사일로 루트 생성
3. `goal.md` 작성
4. 필요한 레포지토리만 사일로 루트에 clone
5. 필요한 `runtime_set`을 확인하고, 서버형 shared runtime은 health gate를 통과했는지 확인
6. 각 레포지토리에서 기준 브랜치 확인 후 작업 브랜치 생성
7. 개발 세션에 `/goal`로 `goal.md 달성 부탁해` 전달
8. 개발자 에이전트가 관련 코드와 QA 증거를 확인하고 수정 수행
9. QA 에이전트가 테스트, agent-browser 검증, report를 실행
10. 리뷰 에이전트가 diff, scope, branch safety, secret policy, SSoT 후보를 검토
11. 실패하면 같은 사일로 안에서 개발자 에이전트에게 재작업 요청
12. 통과하면 diff가 있는 레포지토리만 PR 생성
13. PR 본문에 결과, criteria별 검증 결과, 승격 후보, 비승격 항목 기록
14. project SSoT의 task/issue/인수인계 상태 갱신 후보를 정리
15. 메인 오케스트레이터에게 최종 보고
```

## 사일로 작업 공간 규칙

사일로는 공유 workspace를 직접 더럽히는 장기 작업자가 아닙니다.

기본 원칙:

- 사일로는 그때그때 필요한 레포지토리만 clone합니다.
- clone된 작업 공간은 폐기 가능해야 합니다.
- 사일로는 `main`, `dev`, `develop`, `master` 같은 보호 브랜치에서 직접 작업하지 않습니다.
- 항상 새 작업 브랜치를 생성한 뒤 수정합니다.
- 격리 clone과 작업 브랜치 안에서는 문제 해결에 필요한 코드를 자유롭게 수정할 수 있습니다.
- 격리 clone은 해당 task 수행을 위한 폐기 가능한 source workspace이며, 사일로 개념 자체나 장기 소스 저장 위치가 아닙니다.
- 코드가 크게 망가져도 해당 clone/branch를 폐기하면 됩니다.
- 최종 결과는 PR로만 메인 오케스트레이터에게 제출합니다.

이 구조에서 안전 장치는 "수정 제한"이 아니라 "격리, 브랜치, PR 리뷰, 폐기 가능성"입니다.

## 공용 서비스

사일로별로 매번 clone하거나 수정하지 않는 공용 서비스가 있을 수 있습니다.

예:

- backend API
- shared DB proxy
- 공용 dev server

공용 서비스 운영 기준:

- 메인 오케스트레이터가 세션 동안 하나만 띄웁니다.
- 사일로는 해당 서비스를 검증 대상으로 사용할 수 있습니다.
- 사일로는 기본적으로 공용 서비스를 직접 clone하거나 수정하지 않습니다.
- 공용 서비스 수정 필요성이 발견되면 PR 본문에 `SSoT 승격 후보` 또는 `메인 오케스트레이터 판단 필요`로 남깁니다.

## Shared runtime

shared runtime은 workspace root 아래 여러 task silo가 함께 참조하는 공용 실행 repo 묶음입니다. task silo의 폐기 가능한 clone과 다르게 장기 checkout일 수 있으며, project SSoT 또는 local config의 registry/status로 관리합니다.

기본 경로 후보:

```text
shared-runtime/<project-id>/<runtime-name>/
```

registry/status에는 project id, runtime set, runtime name, runtime kind, repo/remote, branch/commit, purpose, port, env file policy, health check command 또는 URL, owner, last checked, linked tasks를 기록합니다. secret 값은 기록하지 않고 env 파일 path나 secret provider 정책만 기록합니다.

shared runtime을 추가하거나 준비할 때는 `add-shared-runtime` skill을 사용합니다. lifecycle, run, E2E 실행 전 runtime 상태를 확인할 때는 `shared-runtime-health-check` skill을 사용합니다. shared runtime을 삭제하거나 archive 처리할 때는 `delete-shared-runtime` skill을 사용합니다.

## YOLO 모드

사일로 기본 실행 모드는 `yolo`입니다.

`yolo`의 의미:

- 사일로는 수정 전 승인 대기 없이 문제 해결을 우선합니다.
- source code, generated output, test, tooling을 격리 clone 내부에서 자유롭게 수정합니다.
- 접근 가능한 검증 명령과 agent-browser QA를 스스로 실행합니다.
- 실패하거나 방향이 틀리면 해당 clone/branch를 폐기하고 다시 시작할 수 있습니다.
- 완료되면 PR 본문에 수정 범위, 검증 결과, SSoT 승격 후보, 승격하지 않을 항목을 적습니다.

`yolo`에서도 금지되는 것:

- 보호 브랜치 직접 commit 또는 push
- production 데이터 쓰기
- secret 값 읽기 결과를 로그나 문서에 기록
- 공유 브랜치 force push
- SSoT 전역 규칙을 임의 변경

## 사일로가 "자기가 아는 선"에서 고친다는 의미

사일로는 현재 받은 context와 접근 가능한 도구 안에서 최대한 해결합니다.

하지만 아래 경우에는 무리하게 추측하지 않습니다.

- SSoT와 충돌하는 정보가 있음
- 보호 브랜치 직접 수정, production 데이터 변경, secret 기록처럼 YOLO 금지선 밖 변경이 필요함
- 재현은 됐지만 원인이 명확하지 않음
- 다른 프로젝트와 연쇄 변경이 필요함
- 사용자 취향 규칙과 충돌하는 판단이 필요함

이 경우 PR 본문 또는 사일로 보고서에 `메인 판단 필요`로 남깁니다.

## 사일로 내부 이슈/태스크

사일로는 작업 중 새 문제를 발견할 수 있습니다.

예:

- 원래 버그를 고치다 보니 다른 화면도 같은 문제를 가짐
- 테스트는 고쳤지만 generated output 정책이 더 넓게 깨져 있음
- 현재 task보다 큰 구조 문제가 발견됨
- 사용자 취향 규칙이 부족해 판단이 흔들림

이 문제들은 바로 메인 SSoT에 쓰지 않고, 우선 사일로 로컬 발견으로 기록합니다.

이후 PR 시점에 승격 후보로 제출합니다.

## 사일로 종료 상태

| 상태 | 의미 |
|---|---|
| `report-promoted` | 테스트 사일로의 개별 보고서와 evidence 승격 확인 완료 |
| `batch-reported` | 테스트 사일로 묶음의 전체 사일로 보고서 작성 및 승격 후보 정리 완료 |
| `deleted` | 보고서/evidence 승격 gate와 dirty status 확인 뒤 사일로 디렉터리 삭제 완료 |
| `pr-opened` | PR 생성 완료, 메인 리뷰 대기 |
| `needs-rework` | 메인 리뷰 또는 사용자 피드백으로 재작업 필요 |
| `merged` | PR 머지 완료 |
| `blocked` | 사일로 단독으로 해결 불가 |
| `abandoned` | scope 변경 또는 중복으로 폐기 |

## 사일로 생성 원칙

- 사일로는 task/issue 단위로 생성합니다.
- 사일로 생성 시 테스트 사일로인지 일반 사일로인지 먼저 판정합니다.
- lifecycle/e2e/runtime/탐색 검증처럼 보고서가 주 산출물인 임시 실행 환경은 테스트 사일로입니다.
- 구현/수정/문서/repair/conflict/PR 작업처럼 변경/PR/patch/evidence가 주 산출물인 작업 환경은 일반 사일로입니다.
- task 실행 요청은 사일로 생성, `goal.md` 작성, 필요한 repo clone, repo별 작업 브랜치 생성까지 별도 확인 없이 수행합니다.
- 사일로는 현재 workspace 루트의 `task-xxxx/` 같은 보이는 디렉토리에 만듭니다.
- `/tmp` 같은 에이전트 전용 임시 경로는 사용자가 명시하지 않는 한 사일로 기본 위치로 쓰지 않습니다.
- Dynamos 사일로에서 브라우저 확인이 필요하면 `agent-browser`로만 확인합니다.
- 역할별 사일로가 아니라 작업 단위별 사일로입니다.
- QA, 구현, 리뷰 역할은 사일로 내부 또는 메인 루프에서 호출되는 worker입니다.
- 사일로가 만든 모든 중요한 발견은 PR 본문을 통해 메인으로 돌아와야 합니다.
- 사일로는 보호 브랜치가 아니라 새 작업 브랜치에서만 수정합니다.
- 메인 오케스트레이터는 task를 직접 완료 처리하기 전에 먼저 해당 task 사일로가 필요한지 판단합니다.
- 실행 가능한 구현 task는 기본적으로 사일로 생성 후 진행합니다. 예외는 문서 단순 수정, 설정 값 없는 템플릿 수정, 또는 사일로 생성 자체를 고치는 0계층 작업처럼 사일로보다 메인 worktree가 더 적절한 경우입니다.
- 사일로 종료 후에만 task 상태, issue 상태, 인수인계, project SSoT 승격 후보를 갱신합니다.
- 테스트 사일로 삭제 전에는 보고서/evidence 승격 gate와 dirty status 확인이 필수입니다.
- 일반 사일로에는 테스트 사일로 삭제 규칙을 잘못 적용하지 않습니다.
