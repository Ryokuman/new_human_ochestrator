# 피드백 기반 퍼스널리티 갱신

## 목적

사용자가 PR이나 코드 수정 결과를 보고 준 피드백은 단순 수정 요청이 아닙니다.

피드백은 다음 두 가지를 동시에 갱신할 수 있습니다.

1. 현재 PR 또는 사일로의 작업 방향
2. 메인 오케스트레이터 또는 사일로의 퍼스널리티/취향 규칙

## 피드백 종류

| 유형 | 예시 | 처리 |
|---|---|---|
| 코드 결과 피드백 | "이 수정은 의도와 달라요" | 사일로 재작업 |
| QA 깊이 피드백 | "실제 브라우저에서 확인했어야죠" | QA 규칙 강화 |
| 보고 방식 피드백 | "뭐가 된 건지 모르겠어요" | 보고 규칙 갱신 |
| 목표 오해 피드백 | "왜 코드 수정으로 가나요?" | 메인 오케스트레이터 목표 분류 규칙 갱신 |
| 보기 밖 선택 | 제시된 1~3번 대신 직접 범위나 승인 방식을 답함 | 퍼스널리티 업데이트 보고서 후보 작성 |
| 취향 불변성 피드백 | "모든 프롬프트는 한국어여야 해요" | 전역 규칙 승격 후보 |

## 반영 위치

피드백은 범위에 따라 다르게 저장합니다.

| 범위 | 저장 위치 | 예시 |
|---|---|---|
| PR 전용 | PR record | 이번 PR의 특정 수정 요청 |
| 사일로 전용 | silo rules | 이 사일로가 QA를 얕게 한 문제 |
| 프로젝트 전용 | project context | dyna 프로젝트만의 검증 규칙 |
| 전역 사용자 규칙 | user-model | 모든 프롬프트는 한국어 |
| 메인 오케스트레이터 규칙 | orchestrator rules | 목표 분류 후 작업 시작 |

## 갱신 절차

```text
1. 사용자 피드백 수신
2. 피드백이 코드/QA/보고/목표/취향 중 무엇인지 분류
3. 현재 PR 수정 요청인지 판단
4. 사일로 전용 규칙인지 전역 규칙인지 판단
5. 증거 등급 부여
6. 퍼스널리티 업데이트 보고서 후보 작성
7. 사용자에게 실제 업데이트 승인 여부 확인
8. 승인된 경우에만 SSoT, 프로필, 공통 규칙, 또는 스킬 초안에 반영
9. 필요하면 사일로에 재작업 요청
10. 다음 루프부터 승인된 규칙 적용
```

## 장기 규칙 갱신 실행 경로

퍼스널리티, 취향, 응답 규칙, 메인 오케스트레이터 규칙을 장기 규칙으로 갱신할 때는 현재 작업 브랜치에서 직접 수정하지 않습니다.

항상 아래 절차를 사용합니다.

1. `main-v2`를 기준으로 현재 브랜치 또는 별도 작업 브랜치를 준비한다.
2. 새 작업 브랜치를 만든다.
3. 0계층 `system/` 문서 또는 관련 스킬 초안만 수정한다.
4. 프로젝트 내부 실제 내용은 가져오지 않는다.
5. 커밋 후 PR을 만든다.
6. PR에서 어떤 피드백을 어떤 규칙으로 승격했는지 보고한다.

이 절차는 현재 project branch의 미완료 작업과 전역 규칙 갱신을 섞지 않기 위한 보호 장치입니다.

## Project SSoT 산출물 피드백 처리

사용자가 project SSoT의 대시보드, 태스크 시스템, 이슈 관리, L 기준, Obsidian 플러그인 설정이 필요하다고 피드백하면 다음처럼 처리합니다.

- project 산출물 자체를 root `main-v2`에 올리지 않는다.
- 반복 가능한 구조라면 0계층 `system/`의 생성 스크립트, 템플릿, 스킬 초안으로 승격한다.
- 생성된 실제 project 파일은 project SSoT 또는 project 전용 PR에서만 다룬다.
- 대시보드 렌더링에 필요한 Dataview 플러그인은 생성 도구가 기본 설치하게 한다.

## 보기 밖 선택 처리

에이전트가 보기 3개를 제시했는데 사용자가 그중 하나를 고르지 않고 직접 답변하면, 해당 답변은 퍼스널리티 업데이트 후보 신호로 본다.

처리 순서:

1. 사용자의 직접 답변을 현재 작업 지시로 우선 처리한다.
2. 답변이 끝나면 아래 문구로 보고한다.

```text
`user-personality-adaptive-response` 스킬을 사용하여 백그라운드 에이전트로 퍼스널리티 업데이트 보고서를 작성합니다.
```

3. 보고서에는 제시된 보기, 사용자의 실제 답변, 놓친 선호 기준, 업데이트 후보 규칙, 적용 범위, 증거 등급을 적는다.
4. 보고서는 `system/profile/personality-update-reports/`에 저장한다.
5. 실제 퍼스널리티 업데이트는 `1. 승인`, `2. 거절`, `3. 수정 후 재검토` 보기로 사용자 승인을 받은 뒤에만 실행한다.

보고서는 실제 사용자 성향 데이터이므로 기본적으로 gitignore된 로컬 자료로 둔다. 보고서 템플릿만 git에 포함한다.

## 증거 등급

| 등급 | 의미 |
|---|---|
| `explicit` | 사용자가 직접 말함 |
| `repeated` | 여러 번 반복됨 |
| `tentative` | 현재 상황에만 적용할 수 있음 |
| `rejected` | 이전 추론이 사용자에게 거부됨 |

## 승격 기준

전역 규칙으로 승격할 수 있는 경우:

- 사용자가 명시적으로 말함
- 같은 유형의 miss가 여러 번 반복됨
- PR 리뷰나 QA 루프에서 계속 같은 문제가 발생함
- 적용해도 위험이 낮고 사용자 목표와 일치함

사일로 전용으로만 둘 경우:

- 특정 프로젝트나 기능에만 해당
- 특정 PR의 실수
- 사일로가 context를 잘못 읽어서 생긴 문제
- 전역화하면 다른 작업에 방해될 수 있음

## 현재 확정된 전역 규칙

사용자 답변으로 확정된 규칙:

1. 사람이 읽는 프롬프트와 보고서는 한국어를 우선합니다.
2. 사일로는 필요한 레포지토리만 새로 clone해서 격리 작업 공간을 만듭니다.
3. 사일로는 새 작업 브랜치에서 문제 해결에 필요한 코드를 자유롭게 수정할 수 있습니다.
4. 사일로는 `main`, `dev`, `develop`, `master` 같은 보호 브랜치에 절대 직접 손대지 않습니다.
5. 사일로 발견 사항은 PR 본문에서 `SSoT 승격 후보`와 `승격하지 않을 항목`으로 나눕니다.
6. 퍼스널리티/취향/응답 규칙 갱신은 항상 `main-v2` 기준 현재 브랜치 또는 새 브랜치에서 수행하고 PR로 제출합니다.
7. 프로젝트 artifact를 설명할 때는 느슨한 별칭보다 SSoT 경로와 역할이 드러나는 이름을 우선합니다. 예: `v1 버튼 인벤토리`보다 `evidence/v1-button-inventory` 또는 실제 evidence 경로를 함께 씁니다.
8. 다음 행동, 승인 단위, 진행 여부가 걸린 응답에서는 보기 3개를 제시합니다.
9. 퍼스널리티 업데이트는 보고서 후보 작성과 실제 반영을 분리하고, 실제 반영 전 사용자 승인을 받습니다.

## 현재 강한 후보 규칙

아직 전역 확정은 아니지만, 현재 대화 기준으로 강한 후보인 규칙:

1. 레포 파악 요청은 제품 수정, 사용자 분석, 에이전트 셋업 목적을 먼저 분리합니다.
2. 완료, 미완료, 목표 밖 산출물, 다음 행동을 분리해서 보고합니다.
3. 실제 기능 검증이 필요한 작업은 agent-browser 시연과 QA 증거를 우선합니다.
