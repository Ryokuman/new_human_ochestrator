# 갱신 절차

## 기본 흐름

```text
1. 사용자 피드백 또는 퍼스널리티 불일치 신호 수신
2. 현재 작업에 즉시 반영할 내용인지 먼저 판단
3. 피드백 유형 분류
4. PR/사일로 전용인지, 프로젝트 전용인지, 전역 사용자 규칙 follow-up인지 판단
5. 증거 등급 부여
6. `active/`에 로컬 feedback 작성 또는 기존 feedback update
7. 사용자가 원하는 주기로 여는 퍼스널리티 검토 세션에서 `active/` feedback 묶음 분석
8. 검토 결과가 필요하면 퍼스널리티 업데이트 보고서 후보 작성
9. 사용자에게 실제 업데이트 승인 여부 확인
10. 승인된 경우에만 0계층 공통 규칙, 1계층 project 기준, 역할별 agent 프롬프트, 또는 스킬 초안에 반영
11. 필요하면 사일로에 재작업 요청
12. 다음 루프부터 승인된 규칙 적용
```

## 증거 로그 작성 조건

아래 중 하나에 해당하면 장기 반영 여부와 무관하게 로컬 증거 로그를 반드시 남깁니다.

- 사용자가 "이 방식이 아니다", "왜 보기가 없나", "어떤 스킬을 썼는지 모르겠다"처럼 에이전트 행동 방식을 지적함
- 에이전트가 보기 3개를 누락함
- 에이전트가 사용한 스킬을 보고하지 않음
- 사용자가 보기 밖 답변을 통해 승인 방식, 보고 방식, 범위 선택 방식을 직접 교정함
- 같은 종류의 오해가 한 세션 안에서 반복됨

단, 현재 작업 수정이 먼저입니다. 로그 작성은 현재 작업을 멈추는 이유가 아닙니다. 증거 로그는 모든 답변 원문을 장기 저장하는 장치가 아니라, 응답 계약에 영향을 준 사건의 원문 일부, 해석, 즉시 조치, 적용 범위 후보를 기록하는 장치입니다.

## Feedback 상태 디렉토리

로컬 feedback 상태는 디렉토리로 구분합니다.

| 디렉토리 | 의미 | update 기본 포함 여부 |
|---|---|---|
| `active/` | 아직 검토, 적용, 종료 판단이 남은 feedback | 포함 |
| `applied/` | 사용자 승인 뒤 0계층, 1계층, 역할별 프롬프트, 스킬 등에 반영한 feedback | 제외 |
| `closed/` | 반영하지 않기로 정했거나 더 추적하지 않는 feedback | 제외 |

feedback update 때는 기본적으로 `active/`만 읽습니다. `applied/`와 `closed/`는 사용자가 명시적으로 재검토를 요청한 경우에만 포함합니다.

보류 feedback은 별도 `hold/` 디렉토리로 옮기지 않습니다. `active/` 안에 남기고 metadata에 아래 값을 둡니다.

```yaml
status: hold
hold_reason: "<보류 이유>"
review_after: "YYYY-MM-DD 또는 재검토 조건"
```

## 사용자 주도 검토 주기

퍼스널리티 업데이트는 매 feedback마다 장기 규칙으로 반영하지 않습니다. 사용자가 원하는 주기로 별도 검토 세션을 열어 feedback을 분석하고, 시스템 퍼스널리티 갱신 여부를 정합니다.

| 사용자 선택 검토 시점 | 실행 |
|---|---|
| 세션 종료 전 검토 요청 | 이번 세션에서 누적된 `active/` feedback을 훑고 follow-up을 분리합니다. |
| PR 또는 문서 정리 전 검토 요청 | 해당 PR에 반영해야 하는 보고/검증/역할 규칙 follow-up이 있는지 확인합니다. |
| 같은 유형 증거 누적 후 검토 요청 | 반복 패턴으로 보고 업데이트 보고서 후보를 작성합니다. |
| 사용자 명시 요청 | 사용자가 "로그 분석해", "이걸 규칙으로 넣어", "업데이트해", "반영해"라고 하면 즉시 후보 보고서를 작성합니다. |
| 사용자가 정한 유지보수 주기 | `active/` feedback을 정리하고 적용된 것은 `applied/`, 종료된 것은 `closed/`, 보류는 `active/`의 `status: hold`로 갱신합니다. |

## 승인 전 상태

승인 전 feedback 로그와 업데이트 보고서는 follow-up 자료입니다.

- `explicit`이어도 바로 전역 규칙으로 쓰지 않습니다.
- 현재 작업에는 즉시 반영할 수 있습니다.
- 장기 반영은 사용자 승인 후에만 수행합니다.
- 승인되지 않은 단일 응답은 전역 사용자 규칙으로 확정하지 않습니다.

## 장기 규칙 갱신 실행 경로

퍼스널리티, 취향, 응답 규칙, 메인 오케스트레이터 규칙을 장기 규칙으로 갱신할 때는 현재 작업 브랜치에서 직접 수정하지 않습니다.

항상 아래 절차를 사용합니다.

1. `main-v3/main`에서 파생한 별도 작업 브랜치를 준비합니다.
2. 새 작업 브랜치에서 0계층 `system/` 문서 또는 관련 스킬 초안만 수정합니다.
3. 프로젝트 내부 실제 내용은 가져오지 않습니다.
4. 커밋 후 PR을 만듭니다.
5. PR에서 어떤 evidence를 어떤 규칙으로 반영했는지 보고합니다.

이 절차는 현재 project branch의 미완료 작업과 전역 규칙 갱신을 섞지 않기 위한 보호 장치입니다.

## 보기 밖 선택 처리

에이전트가 보기 3개를 제시했는데 사용자가 그중 하나를 고르지 않고 직접 답변하면, 해당 답변은 퍼스널리티 업데이트 후보 신호로 봅니다.

처리 순서:

1. 사용자의 직접 답변을 현재 작업 지시로 우선 처리합니다.
2. 답변이 끝나면 로컬 feedback을 남겼다고 보고합니다.
3. feedback에는 제시된 보기, 사용자의 실제 답변, 놓친 선호 기준, follow-up 규칙, 적용 범위, 증거 등급을 적습니다.
4. 보고서 후보는 즉시 자동 작성하지 않고, 사용자가 원하는 주기로 여는 퍼스널리티 검토 세션에서 작성합니다.
5. 보고서 형식은 [`personality-update-report.template.md`](personality-update-report.template.md)를 따릅니다.
6. 실제 업데이트는 `1. 승인`, `2. 거절`, `3. 수정 후 재검토` 보기로 사용자 승인을 받은 뒤에만 실행합니다.

## 보기 밖 선택 feedback 검증

보기 밖 선택 시스템이 실제로 동작했는지 확인할 때는 아래 세 가지를 검증합니다.

1. `local/personality-feedback-log/feedback/active/`에 feedback 파일이 생성됐는지 확인합니다.
2. 생성 파일이 `git status --ignored`에서 `!! local/` 아래 ignored 상태인지 확인합니다.
3. 파일 본문에 제시된 보기, 사용자의 실제 답변, 놓친 선호 기준, follow-up 규칙, 적용 범위, 증거 등급이 들어 있는지 확인합니다.

이 검증은 feedback이 장기 규칙으로 반영됐다는 뜻이 아닙니다. 장기 반영은 별도 검토와 사용자 승인 후에만 수행합니다.
