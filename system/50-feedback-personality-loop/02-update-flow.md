# 갱신 절차

## 프로젝트의 메인 정신

사용자 개입을 늘려 현재 결과만 개선하지 않습니다. 반복되는 사용자 개입의 원인을 Feedback, User Layer, Project Contract에 반영하여 이후 필요한 사용자 개입을 줄입니다.

## 일반 작업 세션

일반 세션은 퍼스널리티와 관련해서 아래까지만 수행합니다.

1. 사용자 교정을 현재 작업에 즉시 반영합니다.
2. 응답 계약이나 판단 방향에 영향을 준 사건을 `user-layer/feedback/active/`에 Feedback으로 기록합니다.
3. 후보 퍼스널리티를 만들거나 User Layer 반영 승인을 요구하지 않고 원래 작업을 계속합니다.

User Layer가 없어도 작업을 계속합니다. 공개 template을 실제 퍼스널리티로 사용하거나 임의 경로에 Feedback을 만들지 않습니다. 현재 작업에는 교정을 적용하고 최종 보고에 `Feedback 미기록: User Layer 없음`을 남깁니다.

## 퍼스널리티 갱신 세션

사용자가 명시적으로 퍼스널리티 갱신을 요청한 세션에서만 아래 절차를 실행합니다.

```text
active Feedback 검토
→ 범위 라우팅
→ 후보 퍼스널리티 생성
→ 가까운 사례 검증
→ 경계 사례 검증
→ 전이 사례 검증
→ 종료 또는 추가 검증 질문
→ User Layer AGENTS 후보 diff 검토
→ 사용자 승인
→ 유저 퍼스널리티 반영
→ Feedback 상태 이동
```

## 범위 라우팅

Feedback을 후보 퍼스널리티로 바로 승격하지 않습니다.

- 특정 프로젝트의 제품 불변 조건은 Project AGENTS로 보냅니다.
- Project Work 실행 규칙은 Task, Issue, QA, Runbook 또는 `60-feedback-update/`로 보냅니다.
- 현재 Task에만 필요한 조건과 일회성 교정은 장기 퍼스널리티에서 제외합니다.
- 시스템 운영 방식은 Operating Hypothesis 후보와 구분합니다.
- 프로젝트가 달라도 유지되는 사용자 판단 방향만 후보 퍼스널리티로 만듭니다.

## 시나리오 검증

- 가까운 사례: 원래 Feedback과 가까운 상황
- 경계 사례: 판단 기준이 충돌하거나 적용 한계가 드러나는 상황
- 전이 사례: 표면은 다르지만 같은 판단 원리가 적용되어야 하는 상황

각 검증 결과에는 사용자의 선택과 이유, 후보의 예측, 일치·부분 일치·불일치, 후보 수정 또는 기각 이유를 남깁니다. 최소 세 종류 검증이 끝나면 사용자에게 종료할지 더 검증할지 묻습니다. 추가 검증은 다른 영역이나 반례로 진행합니다.

## 반영 경계

- 사용자의 후보 diff 승인이 있어야 `user-layer/AGENTS.md`에 반영합니다.
- 승인된 Feedback은 `applied/`, 기각·중복·일회성·다른 계층 라우팅은 `closed/`로 이동합니다.
- 보류는 `active/`에 유지하고 보류 이유와 재검토 조건을 기록합니다.
- User Layer에는 User Hypothesis 상태 필드를 두지 않습니다.
- Operating Hypothesis와 Task `hypothesis_chain`은 별도 기존 시스템으로 유지합니다.
